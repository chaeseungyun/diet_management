# 끼니 공유(친구) 기능 계획

작성 2026-11-08. 상태: **방향 확정**(2026-11-08 사용자 결정 7건, §9 · [`decisions.md`](decisions.md) DEC-066). 경로·DTO 필드명·테이블 세부는 구현 시 바뀔 수 있는 **제안**이다. 선행 조건인 **식사 사진 업로드**는 별도 계획이 필요하다(§8, §F).

## 1. 목적과 범위

첫 사용 사례는 "연인 둘이 서로 오늘 먹은 끼니를 본다"다. 모델은 처음부터 **N명 친구**로 만들고, 그룹·공개 피드는 뒤에 붙일 수 있게 자리만 둔다.

공유하는 것(확정, §9-2): 날짜별 식사 기록 — 끼니 상태(먹었음·안 먹음·기록 전), 품목명·실제량·단위, 식단 외 식사 메뉴명, **하루 영양 합계**(kcal·탄·단·지, 미상은 미상 그대로), 하루 완료 여부, 식사 사진(사진 업로드 기능이 생긴 뒤). 항목별 끄기 토글은 두지 않고 공개 범위(나만 보기 / 친구 공개)와 친구별 끄기만 둔다.

공유하지 않는 것(DTO 에 아예 넣지 않는다): 재고·구매·가격·입고, **체중·목표 체중**(확정, 1차 비공유), 목표 kcal, 식단표·날짜 예외, 알림 설정, 카카오 ID.

하지 않는 것:

- 타인 기록에 **쓰기**(대신 기록·수정·완료)는 없다. 공유는 읽기 전용이고, 반응(이모지)·댓글·댓글 좋아요만 별도 테이블에 쓴다.
- 전체 공개 피드·검색·추천 친구는 만들지 않는다. 사용자가 서로 초대·수락한 관계만 본다.
- 카카오톡 친구 목록 가져오기는 쓰지 않는다(§2: 비즈 앱 전환·검수·상대 동의가 모두 필요).
- 전화번호·연락처 동기화는 하지 않는다(수집 항목 증가, NFR-04).

| --- | --- | --- |

| 셋로그 | **초대 링크로 들어오면 바로 멤버**, 공개 설정 메뉴 대신 "로그 안의 사람만 본다"는 폐쇄 구조(4~12명). 작은 집단 전제라 공개 범위 UI 가 거의 없다 | 영상·시간 맞춰 찍기, 그룹 전용 모델(1차는 1:1 친구) |

## 3. 설계 원칙 (기존 불변식과의 관계)

- **격리 규칙의 유일한 예외를 한 함수로 좁힌다.** 지금까지 모든 조회는 `userId = 토큰 사용자` 였다(NFR-04). 공유는 처음 생기는 **타인 데이터 읽기**이므로, 접근 판정을 `SharingAccessService.resolveViewable(viewerId, ownerId)` 하나에 두고, 친구 화면용 조회는 모두 이 함수를 거친 뒤에만 `ownerId` 로 읽는다. 판정 실패는 존재 여부와 무관하게 **404**(D-06). 403 은 쓰지 않는다.
- **공유 DTO 는 별도 클래스다.** `DayDto` 를 재사용하지 않고 `SharedDayDto` 를 새로 만들어 필드를 화이트리스트로 고른다. 재고·구매·체중 필드가 실수로 새는 경로를 구조적으로 막는다. e2e 는 응답 키 목록을 단언한다.
- **방향이 있는 공유.** A→B 공개와 B→A 공개는 독립이다. 친구 관계는 대칭이지만 "내 기록을 이 친구에게 보인다"는 각자 끈다.
- **기본은 비공개.** 가입 즉시 아무것도 공개되지 않는다(`visibility=private`). 초대 링크를 만들거나 수락하는 화면에서 "내 끼니를 친구에게 공개" 토글을 바로 보여 켜게 한다(연인 사례에서 한 번의 탭).
- **읽는 쪽 규칙은 기존 계산을 그대로 쓴다.** 친구의 하루도 D-01 계산 함수와 `evaluateDay` 를 쓰고, 미기록 자유 끼니는 숨긴다(D-18). 미래 날짜는 404, 가입일 이후는 **전부** 볼 수 있다(§9-3). 영양 미상은 '미상' 그대로 보인다(null 은 미상).
- **친구가 쓰는 것은 반응·댓글·댓글 좋아요 셋뿐이고, 모두 접근 판정을 통과한 기록에만 쓸 수 있다.** 소유자는 자기 기록의 댓글을 지울 수 있다. 기록이 `unrecorded` 로 되돌아가면 반응·댓글·좋아요를 함께 지운다(식사 기록 쓰기 트랜잭션 안에서).
- **탈퇴·차단은 즉시 끊긴다.** `User.deletedAt` 이 있으면 친구 목록·조회에서 빠지고, 차단은 관계 행을 `blocked` 로 바꿔 재요청·조회를 막는다. 원장·스냅샷처럼 과거를 보존할 필요는 없으므로 친구 끊기는 행 삭제다.
- **업무 규칙은 API 에만**(NFR-07). 초대 코드 생성·만료·접근 판정은 NestJS. 웹은 화면과 공유 시트 호출만.

## 4. 데이터 모델 (제안)

```
users (추가 컬럼)
  friend_code        text UK      -- 8자, base32(혼동 글자 제외), node:crypto. 재발급 가능
  share_visibility   enum default private  -- private | friends  (public 은 enum 에 두지 않고 필요 시 추가, §9-1)
  -- 항목별 공개 플래그는 두지 않는다(§9-2). 공유 묶음은 코드(SharedDayDto)가 정한다

friend_links                          -- 대칭 관계 1행. (user_low_id, user_high_id) 유니크
  id            uuid PK
  user_low_id   uuid FK   -- 두 사용자 id 중 작은 쪽 (중복 쌍 방지, Prisma 복합 유니크로 표현 가능)
  user_high_id  uuid FK
  requested_by  uuid FK   -- 요청·초대한 쪽
  status        enum      -- pending | accepted | blocked
  blocked_by    uuid null -- status=blocked 일 때 차단한 쪽
  low_shares_to_high  bool default true   -- 친구별 끄기 (사용자 기본값 share_visibility 와 AND)
  high_shares_to_low  bool default true
  created_at, responded_at timestamptz

friend_invites                        -- 초대 링크 (셋로그 방식: 수락 즉시 accepted)
  id          uuid PK
  user_id     uuid FK
  code        text UK    -- 12자 이상 랜덤, 열거 불가
  expires_at  timestamptz   -- 기본 7일
  max_uses    int default 1
  used_count  int default 0
  revoked_at  timestamptz null

meal_reactions                        -- 공유-2. 기록 1건에 사용자당 1개
  id              uuid PK
  meal_record_id  uuid FK
  user_id         uuid FK   -- 반응한 사람(기록 소유자 아님)
  emoji           text      -- 허용 목록 중 하나(구현 시 상수로, packages/shared)
  created_at      timestamptz
  UK (meal_record_id, user_id)

meal_comments                         -- 공유-2. 기록 1건에 여러 개, 평면(답글 없음)
  id              uuid PK
  meal_record_id  uuid FK
  user_id         uuid FK   -- 쓴 사람(소유자 본인도 가능)
  body            text      -- 1~500자
  created_at      timestamptz
  deleted_at      timestamptz null   -- 쓴 사람 또는 기록 소유자가 삭제. '삭제된 댓글' 자리 유지 여부는 구현 시
  INDEX (meal_record_id, created_at)

comment_likes                         -- 공유-2. 댓글 1건에 사용자당 1개
  comment_id  uuid FK
  user_id     uuid FK
  created_at  timestamptz
  PK (comment_id, user_id)
```

- `friend_links` 의 `user_id` 두 개는 "사용자 데이터 테이블에 `user_id`" 규칙의 변형이다. 조회는 항상 `WHERE user_low_id = :me OR user_high_id = :me` 로 시작한다. [`erd.md`](erd.md) §3 에 이 예외를 적는다.
- 접근 판정 = `status=accepted` AND 소유자 `share_visibility=friends` AND 소유자→뷰어 방향 플래그 true AND 두 사용자 모두 `deleted_at IS NULL`.
- `meal_reactions`·`meal_comments`·`comment_likes` 는 소유자가 아닌 사용자가 쓰는 **유일한 테이블**이다. 쓰기 전에 같은 접근 판정을 통과해야 하고, 댓글·좋아요 조회도 그 기록을 볼 수 있는 사람에게만 열린다. 기록이 `unrecorded` 로 되돌아가면 셋을 함께 삭제한다(식사 기록 쓰기 트랜잭션 안에서). 사용자 탈퇴 시 그 사용자가 쓴 반응·댓글·좋아요는 하드 삭제한다(계정 삭제 절차, [`ops.md`](ops.md)).
- 사진: `MealPhoto`(DEC-069, 기록당 여러 장, `expires_at`)가 있으면 `SharedDayDto` 에 썸네일·보기용 URL 을 싣는다. URL 은 API 경로(`GET /friends/{userId}/photos/{photoId}`)이며 같은 접근 판정을 거쳐 스트리밍한다. 서명 URL 은 쓰지 않는다. 만료·삭제된 사진은 `expired: true` 자리만 준다.
- 그룹은 1차에 만들지 않는다. 뒤에 `share_groups`·`share_group_members` 를 추가하면 접근 판정에 "같은 그룹 멤버" 조건만 OR 로 붙인다(§8).

## 5. 친구 추가 흐름 (제안)

| 방식 | 흐름 | 결과 | 레퍼런스 |
| --- | --- | --- | --- |
| **초대 링크** (기본) | S-81 '초대 링크 만들기' → `kkinilog.com/invite/{code}` 복사 또는 OS 공유 시트로 카카오톡 전송 → 상대가 열면 로그인(미가입이면 카카오 가입) → S-82 "OO님과 친구가 됩니다" + 내 끼니 공개 토글 → 수락 | 즉시 `accepted`. 링크는 1회·7일 | 셋로그, 카카오 오픈채팅 링크 |
| **친구 코드** | S-81 에서 상대 코드 입력 → 요청 `pending` → 상대 S-80 에 요청 카드 → 수락/거절 | 수락 시 `accepted` | 카카오톡 ID 추가 |
| QR | 친구 코드를 QR 로 표시·스캔(웹 `BarcodeDetector` 지원이 고르지 않아 카메라 스캔은 보류, 표시만) | 코드 입력과 같음 | 카카오톡 QR |

- 코드 검색 허용 토글은 두지 않는다. 대신 코드는 **재발급**으로 무효화한다(카카오 ID 검색 허용의 단순화).
- 초대 링크 미리보기(비로그인)는 초대자 닉네임만 보인다. 그 외 모든 요청은 로그인 필요.
- 카카오 콜백은 `/` 로만 302 한다(D-14). 초대 링크로 들어온 로그인은 웹이 `code` 를 `sessionStorage` 에 두고 `/` 도착 후 S-82 로 보낸다. API 리다이렉트 허용 목록을 늘리지 않는다.
- 차단(확정, §9-4): 차단당한 쪽은 코드·링크로 다시 요청할 수 없다. 코드 요청은 `pending` 을 만들지 않고 정상 요청과 같은 **202** 로 응답해 차단 사실을 노출하지 않는다. 따라서 `POST /friends/requests` 는 차단 여부와 무관하게 항상 202 이고, 보낸 요청 목록에는 차단된 상대가 나타나지 않는다. 초대 링크 수락은 404(링크가 없는 것과 같게).

## 9. 결정 사항 (2026-11-08 사용자 확정, DEC-066)

1. **기본 공개 범위**: `private`. 초대·수락 화면(S-81·S-82)에서 "내 끼니 공개" 토글을 기본 켬으로 보여 한 탭으로 `friends` 가 되게 한다.
2. **공유 항목**: 먹은 식사(끼니 상태)·품목·식단 외 메뉴명·**하루 영양 합계**를 공유한다. 항목별 끄기 토글은 두지 않는다. **체중·목표 체중은 1차 비공유**. 사진은 선행 기능이 생기면 포함.
3. **과거 기간**: 가입일 이후 **전부**. 기간 제한 설정 없음.
4. **차단 노출**: 차단당한 쪽의 코드 요청은 **202**(정상 요청과 같은 응답, `pending` 미생성). 초대 링크 수락은 404.
5. **반응 + 댓글 도입**. 반응은 이모지 1개/사용자, 댓글은 평면(답글 없음) 텍스트, **댓글에 좋아요**. 허용 이모지 목록은 구현 시 `packages/shared` 상수로 정한다.
6. **배치**: 단계 2 완료 → **단계 3 식사 사진 업로드·보관(EXT-02a)** → **단계 4 끼니 공유** 공유-1 → 공유-2 → 공유-3 → 단계 5 OCR → 단계 6 사진 AI 분석(EXT-02b). EXT-02 분할은 DEC-071(§8).
7. **알림 유니크 확장**(`counterpart_user_id` 열)은 알림 구현 시 D-12·D-22 센티널 설계와 함께 확정. 지금은 §6 안을 기본값으로 둔다.

남은 미정(§F): 반응 이모지 목록. 삭제된 댓글의 자리 표시 여부. (사진 보관 정책·용량은 DEC-069, 순서는 DEC-071 로 닫힘.)

## 10. 핵심 테스트 (e2e, 격리 우선)

- 친구가 아닌 사용자의 `GET /friends/{userId}/days/{date}` → 404. 존재하지 않는 userId 도 404(같은 응답).
- `accepted` 이지만 소유자 `visibility=private` → 404. 소유자가 `friends` 로 바꾸면 즉시 200. 친구별 끄기 → 그 친구만 404.
- `SharedDayDto` 키 목록 스냅샷: 재고·구매·체중·목표·카카오 ID 키가 없다. 영양 합계·식단 외 메뉴명·완료는 항상 들어 있다(§9-2).
- 초대 링크: 1회 사용 뒤 두 번째 수락 404, 만료 뒤 404, 자기 링크 422, 철회 뒤 404. 코드 열거 방어(12자 이상 랜덤).
- 친구 끊기 뒤 양쪽 모두 404. 차단 뒤 코드 요청은 **202 이면서 `pending` 행이 없고**, 응답 본문이 정상 요청과 같다(§9-4). 탈퇴(`deletedAt`) 사용자는 목록·조회에서 빠진다.
- 미래 날짜 404, 가입 전 날짜 404, 가입일 당일부터 오늘까지는 어느 날이든 200(§9-3). 미기록 자유 끼니가 응답에 없다(D-18). 영양 미상은 null 그대로.
- 공유-2: 소유자가 기록을 `unrecorded` 로 되돌리면 반응·댓글·좋아요가 함께 삭제된다. 접근 불가 기록에 반응·댓글 쓰기 404, 볼 수 없는 기록의 댓글에 좋아요 404. 댓글 삭제는 쓴 사람·기록 소유자만 204, 제3의 친구는 404. 501자 댓글 422. 같은 사용자의 좋아요 재요청은 멱등(200, 행 1개).
- 기존 전체 스위트: 공유 기능 추가 뒤에도 단계 0 격리 시나리오 7 이 그대로 통과한다.
