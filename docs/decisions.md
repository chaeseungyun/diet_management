버전: v0.1 (2026-11-03) / 관련 문서: [`requirements-phase1.md`](requirements-phase1.md), [`extension-todo.md`](extension-todo.md), 원본 [`archive/diet-app-requirements-v0.1.md`](archive/diet-app-requirements-v0.1.md)

## 이 문서의 목적과 사용 규칙

이 문서는 앱을 만들면서 내린 **모든 의미 있는 결정과 그 근거**를 시간순으로 남긴다. 요구사항 문서는 "무엇을 만들 것인가"를 담고, 이 문서는 "왜 그렇게 정했고 무엇을 버렸는가"를 담는다. 추후 이력서·포트폴리오에서 설계 판단의 근거로 인용한다.

- 결정 하나당 항목 하나. 번호는 `DEC-###`로 부여하고 재사용하지 않는다.
- 결정이 뒤집히면 기존 항목을 지우지 않는다. 상태를 `대체됨`으로 바꾸고 새 항목에서 `대체: DEC-###`를 적는다. 번복한 이유 자체가 포트폴리오 재료다.
- 상태 값: `확정`(사용자가 합의) / `제안`(구현 기본값·기술 권고, 사용자 미확정) / `미정`(결정 필요) / `대체됨`.
- 요구사항 문서의 확정/제안/미정 구분과 충돌하면 요구사항 문서가 우선하고, 이 문서를 고친다.
- 구현 중 결정(라이브러리 선택, 스키마 변경, 버그 수정 과정의 설계 변경)은 커밋·PR 링크와 함께 바로 추가한다. 나중에 몰아서 쓰면 근거가 사라진다.

각 항목 형식:

```
### DEC-### 제목
- 날짜 / 상태 / 범위(요구사항 ID)
- 맥락: 어떤 문제·제약이 있었나
- 선택지: 고려한 대안 (버린 이유 포함)
- 결정: 무엇을 하기로 했나
- 근거: 왜 이 선택인가
- 영향·트레이드오프: 얻는 것과 감수하는 것
- 재검토 조건: 언제 다시 보나
- 포트폴리오 포인트: 이 결정이 보여 주는 역량 (선택)
```

## A. 프로젝트 운영 방식

### DEC-001 요구사항을 1차·확장·원본으로 분리
- 날짜 2026-11-03 / 상태 확정 / 범위: 문서 구조
- **맥락**: 원본 요구사항 v0.1 한 파일에 1차 기능(로그인·기록·재고)과 확장 기능(OCR·사진 분석·크롤링·LLM 추천)이 섞여 있었다. 구현 에이전트(Claude Code)에게 전달하면 확장 기능까지 한 번에 만들려 하거나, 1차 설계가 확장 요구에 끌려갈 위험이 있었다.
- **선택지**: (a) 단일 문서 유지 + 단계 표시만 강화, (b) 1차/확장 두 문서로 분리하고 원본은 아카이브.
- **결정**: (b). `requirements-phase1.md`(단계 0~2), `extension-todo.md`(단계 3 이후 + 확장 전용 NFR), `archive/`(원본 보존).
- **근거**: 구현 시 읽는 문서의 범위가 곧 작업 범위가 된다. 확장 전용 비기능 요구(AI 비동기 처리, 사진 개인정보, AI 비용 차단)가 1차 NFR에 섞여 있으면 1차 구현이 불필요하게 무거워진다. 원본을 지우지 않은 것은 분리 과정의 누락을 추적하기 위해서다.
- **영향·트레이드오프**: 두 문서 간 교차 참조를 유지해야 한다. 1차 설계가 확장을 막지 않도록(영양 출처에 "AI 추정" 값 예약, AI 예산 슬롯) 확장 문서를 "참고만" 하는 규칙을 두었다.
- **재검토 조건**: 단계 3 착수 시 `extension-todo.md`를 정식 요구사항으로 승격.
- **포트폴리오 포인트**: AI 코딩 에이전트에게 전달하는 문서의 범위 통제 자체를 설계 대상으로 본 사례.

### DEC-002 확정/제안/미정 3단계 표기 체계
- 날짜 2026-11-03 / 상태 확정 / 범위: 문서 전체
- **맥락**: 요구사항 초안은 사용자 요구와 작성자(AI)의 기술 권고가 같은 문장 톤으로 섞여 있었다. 수치 목표(p95 500ms, 백업 7일)나 스택 선택이 "사용자가 정한 것"으로 오해될 수 있었다.
- **결정**: 모든 항목에 `[확정]` / `[제안]` / `[미정]`을 표기한다. 확정 = 사용자와 합의, 제안 = 구현 기본값·기술 권고, 미정 = 구현·결제 전 결정 필요. 요구사항 §6의 사용자 확정 설계 결정은 FR 본문과 충돌 시 우선한다.
- **근거**: 결정권의 소재를 명확히 해야 나중에 "왜 이렇게 됐지"를 추적할 수 있고, 제안을 바꿀 때 사용자 재합의가 필요한지 즉시 알 수 있다. 이 결정 기록 문서의 상태 값도 같은 체계를 쓴다.
- **영향·트레이드오프**: 문서가 다소 길어진다. 대신 AI 에이전트가 "미정을 확정으로 기록하지 않는다"는 규칙을 기계적으로 따를 수 있다.

### DEC-003 1차 범위를 단계 0~2로 한정, 자동 주문 등 제외
- 날짜 2026-11-03 / 상태 확정 / 범위: §0
- **맥락**: 아이디어 단계에서 OCR, 사진 분석, 크롤링, 쿠팡 자동 장바구니, 소비기한 관리 등 많은 기능이 나왔다.
- **선택지**: 전체 비전을 1차에 넣기 vs. 매일 쓸 수 있는 최소 흐름만 먼저.
- **결정**: 1차 = 로그인 → 수동 제품·구매 등록 → 반복 식단·예외 → 섭취 기록 → 칼로리·탄단지 → 체중 → 재고·소진 예측 → 알림 → 대시보드 → 직접 배포. 자동 주문·결제, 쿠팡 자동 장바구니, 소비기한·개봉일 관리, 소스 재고 차감은 제외·보류.
- **근거**: (1) 주당 5시간이라는 시간 제약(DEC-004). (2) 재고·기록의 정합성이라는 핵심 가치는 AI 없이도 검증 가능하다. (3) 자동 주문은 연동 가능성이 미검증이고 결제 리스크가 있다. (4) 소비기한 관리는 입력 부담을 늘려 "적은 입력"이라는 목적과 충돌한다.
- **영향·트레이드오프**: 외부 식사 영양은 1차에서 수동 입력뿐이다. 메뉴명으로 자동 계산되는 것처럼 보이는 UI를 만들지 않기로 하여 기대치를 관리한다.

### DEC-004 주당 5시간 제약 아래 "작게 배포·피드백" 개발 방식
- 날짜 2026-11-03 / 상태 확정 / 범위: §0, §4
- **맥락**: 개발 가능 시간은 주당 약 5시간. 출시일은 미정.
- **결정**: 단계 0(로그인 배포) → 1(매일 쓸 수 있는 기록 + 재고 원장 쓰기, DEC-046) → 2(재고 화면·예측·알림)로 나누고, 각 단계를 실제 배포해 본인이 쓰면서 다음 단계를 진행한다. 일정은 예상치로만 두고 확정 일정으로 표현하지 않는다.
- **근거**: 시간이 적을수록 배포되지 않은 코드의 가치가 0에 수렴한다. 단계 0에 HTTPS·백업·복원 확인을 넣은 것은 운영 리스크를 가장 먼저 드러내기 위해서다.
- **포트폴리오 포인트**: 제약 조건을 전제로 한 우선순위 결정.

### DEC-005 처음부터 다중 사용자 데이터 격리 설계
- 날짜 2026-11-03 / 상태 확정 / 범위: §0, NFR-04, FR-01

### DEC-035 pnpm 모노레포 + Prisma + OpenAPI 타입 생성
- 날짜 2026-11-05 / 상태 확정 / 범위: 요구사항 §3·§5, D-05
- **맥락**: DEC-006/007이 "프런트·백엔드 타입 공유"를 근거로 삼았는데, 실제 공유 수단(리포 구조·ORM·DTO 전달 방식)이 미정이었다. 첫 커밋의 폴더 구조와 마이그레이션 도구는 되돌리는 비용이 가장 크다.
- **선택지**: (a) 리포 2개 분리 + npm 패키지로 타입 배포, (b) pnpm 모노레포(`apps/web`, `apps/api`, `packages/shared`), (c) Next 단일 리포 안에 Nest 포함. ORM은 Prisma / TypeORM / Drizzle. 타입 공유는 DTO 패키지 수동 관리 / Swagger→OpenAPI→코드 생성.
- **결정**: (b) pnpm 모노레포. ORM은 Prisma. NestJS Swagger로 OpenAPI를 생성하고 프런트 API 타입을 그 산출물에서 생성한다. `packages/shared`에는 enum·상수·순수 계산 함수만 둔다.
- **근거**: (1) 한 PR에서 API와 화면을 같이 바꿀 수 있다. (2) Prisma는 `Decimal`·마이그레이션·타입 생성이 기본 제공이라 주당 5시간 제약에 맞다. (3) 생성된 타입을 쓰면 DTO 중복 정의(NFR-07의 중복 금지)가 구조적으로 막힌다.
- **영향·트레이드오프**: Prisma의 트랜잭션 API(`$transaction` 대화형)로 재고 트랜잭션을 작성해야 하며, 원시 SQL이 필요한 집계(`SUM(delta)`)는 `$queryRaw`로 보완한다. OpenAPI 생성 단계가 CI에 추가된다.
- **재검토 조건**: Prisma가 append-only 원장·부분 유니크 인덱스를 다루기 불편하다고 판단될 때(Drizzle 전환 검토).
- **포트폴리오 포인트**: 타입 공유를 "말"이 아니라 빌드 파이프라인으로 강제한 설계.

### DEC-036 타인 리소스 요청은 403이 아니라 404
- 날짜 2026-11-05 / 상태 확정 / 범위: NFR-04, api §0, D-06
- **맥락**: 다른 사용자 소유의 ID로 요청했을 때 "권한 없음(403)"을 돌려주면 그 ID가 존재한다는 사실이 새어 나간다.
- **선택지**: 403(의미상 정확) / 404(존재 여부 비노출).
- **결정**: 존재하지 않는 리소스와 타인 리소스 모두 `404`. `403`은 쓰지 않는다. 격리 테스트(시나리오 7)는 404를 단언한다.
- **근거**: 사용자는 "원래는 403이지만 보안·개인정보 노출 문제로 404"라는 취지에 동의했다. 식단·체중은 개인정보이고 ID 존재 여부도 정보다.
- **영향·트레이드오프**: 디버깅 시 "내가 ID를 잘못 넣었는지, 남의 것인지" 구분이 안 된다. 서버 로그에는 사유를 남기되 응답에는 싣지 않는다.

### DEC-037 인증 세션은 stateless JWT + HttpOnly 쿠키, 서버 세션 저장소 없음
- 날짜 2026-11-05 / 상태 확정 / 범위: NFR-04, D-07
- **맥락**: ERD A8이 세션 저장소를 미결로 두었다. 단계 0 로그인 구현의 첫 선택이고 쿠키·CSRF·로그아웃·만료 처리가 모두 여기에 종속된다.
- **선택지**: (a) DB 세션 테이블 + 불투명 세션 ID 쿠키, (b) Redis 세션, (c) 서버가 서명한 JWT를 HttpOnly 쿠키에 담는 stateless 방식.
- **결정**: (c). 사용자 지시: "서버는 stateless 해야 함. JWT + httpOnly 쿠키". 세션 테이블·Redis를 두지 않는다. 로그아웃은 쿠키 삭제, 만료는 토큰 `exp`.
- **근거**: (1) 서버 상태가 없어 프로세스 재시작·수평 확장에 영향이 없다. (2) 2GB VM에서 Redis를 추가하지 않는다. (3) 사용자 5명 규모에서 세션 조회 테이블의 이점이 작다.
- **영향·트레이드오프**: 만료 전 토큰을 서버에서 즉시 무효화할 수 없다(1차 범위 밖). 계정 삭제 시에는 `User.deleted_at`을 요청마다 확인해 거부한다. 서명 키 유출 시 전체 재발급이 필요하므로 키는 환경 변수로만 둔다.
- **미정**: 만료 기간·갱신 토큰 여부·SameSite 값·Origin 검사(요구사항 §7-6, 제안: 7일·갱신 없음·Lax + Origin 검사).
- **포트폴리오 포인트**: 상태 없는 API 서버 설계와 그 한계(즉시 무효화 불가)를 명시한 결정.

### DEC-038 개발 중 카카오 리다이렉트는 localhost, 출시 정책은 도메인 확정 후
- 날짜 2026-11-05 / 상태 확정(개발) / 미정(출시) / 범위: DEC-015, D-07
- **결정**: 카카오 개발자 앱의 리다이렉트 URI에 `localhost`를 등록해 단계 0을 로컬에서 진행한다. 출시 대상 계정 정책(테스트 계정 등록 vs 검수)은 도메인·VM 구매(2026-11-06 예정) 후 결정한다.
- **근거**: 도메인 없이도 로그인 흐름·격리 테스트를 끝낼 수 있어 배포 전 단계까지 개발을 막지 않는다.

### DEC-045 카카오 콜백은 API가 받고, 웹·API는 같은 오리진에서 경로로 분기
- 날짜 2026-11-05 / 상태 확정 / 범위: NFR-04, D-07, D-14, api §1, screens S-02
- **맥락**: screens는 `/auth/kakao/callback`을 웹 화면(S-02)으로, api는 `/api/v1/auth/kakao/callback`을 API로 적어 콜백 수신자가 둘이었다. DEC-037로 쿠키를 API가 발급하므로 수신자가 정해져야 쿠키 도메인·CORS가 정해진다.
- **선택지**: (a) 웹이 콜백을 받아 code를 API에 전달, (b) API가 콜백을 받아 쿠키 발급 후 웹으로 302. 오리진은 (i) 서브도메인 분리(`api.`), (ii) 같은 오리진에서 `/api/*` 경로 분기.
- **결정**: (b) + (ii). 운영은 Caddy, 개발은 Next rewrite. S-02 화면은 삭제. 실패는 `/login?error=1`로 302 하고 사유를 싣지 않는다.
- **근거**: (a)는 code를 한 번 더 전달해 공격면이 늘고 화면 하나가 더 필요하다. 같은 오리진이면 쿠키 `Domain`·CORS·preflight가 전부 사라져 단계 0 구현량이 줄고 SameSite 설정이 단순해진다.
- **영향·트레이드오프**: 리버스 프록시 설정이 배포 필수 요소가 된다. 서브도메인 분리가 필요해지면(예: 별도 워커 노출) 재검토.

### DEC-016 제품 등록은 구매 목록 우선 방식 B

### DEC-017 제품 정보와 구매·입고 건의 분리

### DEC-018 임의 단위 환산 금지

### DEC-019 미입력은 null, 0과 구분

### DEC-020 과거 섭취 기록은 스냅샷으로 보존

### DEC-022 계획 식사는 저장하지 않고 그때그때 계산 (요구사항 D-01)

- **포트폴리오 포인트**: 파생 데이터를 저장하지 않고 단일 계산 함수로 통일한 설계.

### DEC-024 영양 미상 스냅샷의 사후 보완 (요구사항 D-03)
- 날짜 2026-11-03 / 상태 확정(사용자) / 범위: NFR-02, FR-02, FR-06
- **맥락**: DEC-016으로 영양 없이 등록한 제품을 먹은 기록은 영양 미상 스냅샷이 된다. DEC-020 불변 원칙을 그대로 적용하면 영원히 통계에서 빠진다.
- **선택지**: (a) 불변 유지, 미상은 영원히 미상, (b) 영양 입력 시 자동 소급, (c) 미상 스냅샷만 사용자 확인 후 보완.
- **결정**: (c). 건수를 보여 주고 적용 여부를 묻는다. 이미 값이 있는 스냅샷은 건드리지 않는다. 보완된 스냅샷은 출처 "사후 보완"과 시각을 남긴다.
- **근거**: (a)는 방식 B의 가치를 깎고, (b)는 사용자가 모르는 사이 과거 통계가 변해 불변 원칙 위반이다. (c)는 "값이 있던 것은 안 바뀐다"는 불변의 본질을 지키면서 미상만 채운다.

### DEC-025 식사 상태 3×3 전이와 "상태 설정" API, 버전 충돌 409 (요구사항 D-04)
- 날짜 2026-11-03 / 상태 확정(사용자) / 범위: FR-05, NFR-02
- **맥락**: 중복 클릭·네트워크 재전송·동시 수정에서 재고가 이중 차감되면 안 된다. "취소"의 의미와 하루 완료 후 수정 가능 여부도 모호했다.
- **선택지**: (a) 델타 API(`+2팩 먹음`, `-1팩 취소`) + 멱등성 키, (b) 상태 설정 API(`PUT /meal-records/{date}/{slot}` with `{status, items[], version}`)에서 서버가 이전 스냅샷과의 차이로 `StockMovement`를 생성.
- **결정**: (b). 상태는 미기록/먹었음/안 먹음 세 가지, 어느 상태로든 직접 전이 허용. UI "취소" = 미기록으로 설정(재고 복구, 알림 재개). `version` 불일치는 409. 멱등성 키는 순서가 뒤바뀐 재전송을 막는 보조 수단. 하루 완료 후 수정이 일어나면 완료 해제.
- **근거**: 델타 방식은 재전송을 멱등성 키에 전적으로 의존하고 키가 유실되면 이중 반영된다. 상태 설정 방식은 같은 요청의 재전송이 차이 0이라 본질적으로 무해하다. 낙관적 잠금(`version`)으로 동시 수정을 감지한다. "다르게 먹음"을 상태가 아닌 동작으로 둔 것은 상태 조합 폭발을 막기 위해서다.
- **영향·트레이드오프**: 클라이언트가 항상 전체 상태를 보내야 한다. 모바일에서 항목 수가 적어 부담 없음.
- **포트폴리오 포인트**: 멱등성·동시성을 API 설계 수준에서 해결한 사례. 인수 시나리오 3·4로 검증.

### DEC-042 제품 단위 모델 보강: `unit_label`·`units_per_package`, 영양 기준 단위에서 `serving` 제거
- 날짜 2026-11-05 / 상태 확정 / 범위: FR-02, FR-03, D-02, D-11, ERD Product·ProductNutritionVersion·MealTemplateItem·MealItemSnapshot
- **맥락**: 정합성 검토에서 세 가지가 드러났다. (1) 영양 기준 단위 `serving`을 섭취량(g·ea)으로 환산할 컬럼이 없어 "1회분당 120kcal" 제품의 섭취 영양을 계산할 수 없었다. (2) 구매 수량(포장 단위)을 입고 수량(재고 단위)으로 바꾸는 규칙이 없었고 `package_amount`의 의미가 g 제품(재고량)과 ea 제품(팩 무게)에서 달랐다. (3) D-02는 "팩/개"를 말하지만 enum은 `ea` 하나라 "0.5팩" 표기를 만들 수 없었다.
- **선택지**: (1) `serving_amount` 컬럼 추가 vs `serving` 제거 후 기준량을 재고 단위 수량으로 입력. (2) `package_amount`를 유지하고 환산 규칙을 분기 vs `units_per_package` 하나로 통일. (3) enum에 `pack` 추가 vs 표시용 `unit_label`.
- **결정**: `serving` 제거(기준량은 g/ml/ea, 제품 `stock_unit`과 같거나 `pack_weight_g` 있는 ea 제품에 한해 g). `package_amount`·`package_unit` 제거, `units_per_package`(포장 1개 = 재고 단위 N) 추가, 입고 = 구매 수량 × N(수정 가능). `unit_label` 추가(ea 제품 표시 단위명). `MealTemplateItem.unit`·`MealItemSnapshot.unit`도 g/ml/ea만. 소스 `default_serving_amount`는 `stock_unit` 기준.
- **근거**: 환산 경로를 "재고 단위 ↔ g" 하나로 고정하면 D-02·D-18의 임의 환산 금지가 코드 한 곳에서 검증된다. `serving_amount`를 두면 환산 경로가 둘이 되어 "가루 45g ≠ 단백질 45g" 류의 오류 표면이 늘어난다. enum에 `pack`을 넣으면 계산 규칙은 `ea`와 같은데 분기만 늘어난다.
- **영향·트레이드오프**: "1회분 기준" 영양을 입력하려면 사용자가 1회분의 g(또는 개수)를 알아야 한다. 표시값에 1회분 g가 적혀 있으므로 입력 부담은 작다. ea 제품에 `pack_weight_g`가 없으면 g 기준 영양을 저장할 수 없고 ea 기준으로만 입력한다.
- **재검토 조건**: OCR(EXT-01)이 "1회 제공량" 단위로 값을 뽑을 때 변환 UI가 필요해지면.

### DEC-043 원장 이동이 있는 제품의 `stock_unit` 변경 금지
- 날짜 2026-11-05 / 상태 확정 / 범위: FR-03, NFR-02, D-13, api §3

### DEC-028 통계는 완전한 날만 평균에 포함, 미기록 ≠ 0
- 날짜 2026-11-03 / 상태 확정(2026-11-08, 세부는 DEC-068) / 범위: FR-06
- **결정**: 주간·월간 평균은 하루 기록 완료 + 해당 영양 지표 완전인 날만 포함. 유효일 수/전체일 수와 제외 이유를 표시. 불완전 합계는 "기록된 합계"로 명시. "하루 기록 완료"와 "영양 계산 완료"를 구분. 연속 기록은 체중·식단 준수가 아닌 기록 완료 기반. 계획 실천율은 외부 식사로 사전 변경한 날을 분모에서 제외.

### DEC-029 하루 완료는 사용자 명시 조작

### DEC-030 알림은 명시 허용 슬롯만, 예약 작업 + 중복 방지

### DEC-032 PWA 설치 가능 구조, 오프라인 변경은 1차 제외

### DEC-033 AI·OCR·크롤링은 확장 단계, Python 워커·Redis는 필요 시

### DEC-044 알림 중복 방지 유니크는 NULLS NOT DISTINCT, 취소 시 행을 되돌림
- 날짜 2026-11-05 / 상태 확정 / 범위: FR-09, NFR-05, D-04, D-12, ERD NotificationDelivery
- **맥락**: (1) 유니크 (user, type, target_date, slot, product_id)에서 식사 알림은 `product_id`가, 소진 알림은 `slot`이 NULL이다. PostgreSQL 기본 유니크는 NULL을 서로 다른 값으로 보므로 중복 삽입이 통과해 NFR-05 "중복 방지"가 깨진다. (2) D-04는 취소 시 알림 재개를 확정했는데, 같은 키의 `skipped` 행이 남아 있으면 새 pending 행을 만들 수 없다.
- **선택지**: (1) `UNIQUE NULLS NOT DISTINCT`(PG15+) / `COALESCE` 식 인덱스 / NULL 대신 센티널 값. (2) 재개 시 새 행 삽입 / 기존 행 status 되돌림 / 유니크에 attempt 번호 포함.
- **결정**: (1) `UNIQUE NULLS NOT DISTINCT`, Prisma 원시 SQL 마이그레이션으로 생성. (2) 기존 `skipped` 행을 `pending`으로 되돌리고 `scheduled_at` 재계산. `sent` 행은 재발송하지 않는다.
- **근거**: 센티널 값은 FK와 충돌하고, 식 인덱스는 ORM 타입에 드러나지 않는다. 행을 되돌리면 "한 식사·한 유형·한 날에 행 하나"라는 모델이 유지되어 재시작 중복 차단 로직이 단순하다.
- **영향·트레이드오프**: PostgreSQL 15 이상이 필요하다(Docker 이미지 버전 고정). 이력이 "한 행의 상태 변화"로 남아 발송 횟수 감사는 별도 로그가 필요하다.

### DEC-054 D-03 보완 흐름은 2단계(저장 응답 건수 + backfill 호출)
- 날짜 2026-11-06 / 상태 확정 / 범위: D-03, D-16, api §3·§12-7, S-33
- **맥락**: 영양 저장 시 미상 스냅샷을 같이 채울지 묻는 흐름을 저장 요청의 플래그(1단계)로 할지, 저장 응답의 건수 + 별도 호출(2단계)로 할지. 사용자는 단계 1 착수 시 Claude Code 권고에 위임했다.
- **선택지**: (a) `applyToUnknown` 플래그 1단계, (b) 응답 `unknownSnapshotCount` + `POST …/nutrition/backfill` 2단계.
- **결정**: (b).
- **근거**: 저장이 보완 질문에 막히지 않고, S-33 의 "저장 → N건 발견 → 적용 여부" 다이얼로그와 그대로 맞는다. backfill 은 kcal null 스냅샷만 건드리는 멱등 작업이라 재호출이 안전하다. 플래그 방식은 저장 전에 건수를 미리 알아야 해서 조회가 하나 더 필요하다.
- **영향·트레이드오프**: 호출이 2번. 보완 전에 사용자가 화면을 떠나면 미상이 남지만, 다음 저장 때 다시 묻는다.
- **주의**: 2026-11-05 저녁 Claude Code 가 사용자에게 이 결정을 "1단계 플래그 권고" 로 잘못 설명했다(문서의 '1단계/2단계'를 구현 단계로 오독). 실제 구현은 문서 권고(2단계)대로이며 사용자에게 정정 보고했다.

### DEC-055 단계 1 스키마·동시성 세부
- 날짜 2026-11-06 / 상태 확정(구현) / 범위: erd.md, D-08, D-10, 요구사항 §7-7, DEC-052
- **결정**:
  - DB 제약은 Prisma 스키마로 표현 가능한 것만 쓴다. 부분 유니크 인덱스와 `NULLS NOT DISTINCT` 는 쓰지 않는다. CI 의 `migrate diff --exit-code` 검사가 원시 SQL 제약을 "차이" 로 보기 때문이다. 현재 영양 버전 1건은 서비스가 트랜잭션에서 보장하고, 추가 간식은 `meal_records.seq`(정규 슬롯 0, extra 는 1,2,…)로 `(user, date, slot, seq)` 유니크를 만든다(D-10 의 `id` 식별은 유지). 단계 2 의 `NotificationDelivery` 유니크(D-12)는 NULL 대신 센티널 값을 쓰는 방식으로 다시 검토한다.
  - 식사 기록 동시 수정: `updateMany({ where: { id, version } })` 로 version 을 조건부 갱신해 행을 잠근 뒤에만 원장·스냅샷을 건드린다. 같은 version 의 동시 요청은 먼저 커밋한 쪽만 통과, 나머지는 409. 조회 후 비교 방식은 e2e 에서 이중 차감이 재현됐다.
  - 멱등성: `idempotency_keys` 행을 본 작업과 같은 트랜잭션에서 `INSERT … ON CONFLICT DO NOTHING` 으로 먼저 넣고, 충돌이면 `SELECT … FOR UPDATE` 로 진행 중 트랜잭션을 기다린 뒤 저장 응답을 돌려준다. 다른 본문은 422. 실패하면 키 행도 롤백된다.
  - 원장 복구는 레코드 단위 순 차감(`meal_record_id` 로 묶은 consume/consume_reverse 합)을 제품별로 되돌린다. 스냅샷이 교체돼 `meal_item_snapshot_id` 가 null 이 돼도 식사와의 연결은 남는다.
  - 요구사항 §7-7 기본값 전부 채택(D-17). `MealRecord.kind` 는 `home|outside`, `weekday` 는 ISO 1~7, 보관 거부 422, 자식 테이블은 부모 조인으로 격리.
  - 소스(`is_stock_tracked=false`) 입고는 `StockReceipt` 만 남기고 원장 이동은 만들지 않는다(D-09). 초기 재고 등록은 소스에 허용하지 않는다(422).
  - 외부 식사 예정(미기록) 슬롯은 '계획 포함 예상' 합계에 미상 1건으로 센다. 메뉴명으로 추정하지 않는다.
- **근거**: CI 검사 유지, 재고 이중 차감 방지(NFR-02), 문서 권고 준수.
- **재검토 조건**: Prisma 가 부분 인덱스를 지원하거나 CI 검사를 바꿀 때.

### DEC-059 '계획 없음' 은 자유 끼니, 쓰는 끼니는 사용자 설정, 날짜 예외는 끼니 화면에서도
- 날짜 2026-11-07 / 상태 확정(D-18) / 범위: 요구사항 §7-2, DEC-029 미정 항목, erd User, S-03·S-10·S-11·S-22·S-70, api `PATCH /me`·`GET /days`
- **맥락**: 사용자 질문 — "계획 없음이 잘못된 걸까? 아침은 안 먹어도 되는 것으로 생각하는데 매일 아침은 계획이 없는 건가? 외부 식사를 미리 넣을 수 없나? 캘린더 탭에 들어가야만 되는 게 좋은 방식인가?" 단계 1 코드에서 `none` 은 세 상황(설정 안 함 / 원래 안 먹음 / 먹으면 적는 자유 끼니)을 한 이름으로 보여 주고 있었다.
- **결정**:
  - `none` 의 의미를 "식단에 포함하지 않는 끼니" 로 못 박고 화면 문구를 **자유 끼니** 로 바꾼다. `skip` 유형은 만들지 않는다(자유 끼니와 결과가 같고 격자·완료·통계가 복잡해진다).
  - 집계: 미기록 자유 끼니만 완료·통계·예상에서 제외. 먹었음·안 먹음으로 기록하면 포함. API 는 이미 그렇게 세고 있었고, 날짜 요약(`GET /days`)에서 기록된 자유 끼니를 활성·기록 슬롯에 넣도록 보정했다.
  - `User.active_slots`(MealSlot[], 기본 5개, 1개 이상, extra 불가). `GET /days/{date}`·`GET /days` 는 쓰는 끼니만 돌려주되 기록이 있는 숨긴 끼니는 포함한다. 주간 격자도 쓰는 끼니 행만. 첫 설정·설정 화면에 체크박스.
  - 오늘 화면: 미기록 자유 끼니는 "자유 끼니 · 먹었으면 눌러서 기록: 아침 · 야식" 한 줄로 접는다.
  - S-11 에 "이 날은 다르게 먹을 예정" → 고정 식단/외부 식사/자유 끼니 + 메모 → `PUT /plans/overrides/{date}/{slot}`. 아직 먹지 않은 오늘·미래 끼니에만 보이고, 예외가 있으면 해제도 된다. 캘린더의 기간 일괄 변경은 그대로.

  - `PUT` 본문 `skipUnrecordedFree=true` 면 미기록 자유 끼니를 **같은 트랜잭션**에서 `skipped` 로 저장한 뒤 완료한다. S-14 "뭔가 드셨나요? 아니오" 한 탭이 서버 왕복 한 번이고, 중간에 실패하면 아무것도 저장되지 않는다. 기록 쓰기는 기존 `write()` 를 그대로 거치므로 version 잠금·완료 해제 규칙이 같다.
  - `nutritionComplete` = 기록된 합계(먹었음 + 안 먹음 0 + 추가 간식)의 `complete`. 미기록 자유 끼니는 합계에 없으므로 영향 없다. 재완료는 upsert 로 `nutritionComplete` 만 갱신하고 `completedAt` 은 유지한다(D-03 보완 뒤 다시 누르면 '영양 완전' 으로 바뀔 수 있다).
  - `DELETE` 는 없는 날도 204(멱등). 완료는 목표 달성과 무관하다(D-20).
  - S-14 는 미기록 자유 끼니가 있을 때 **아니오 / 기록하기** 두 버튼을 주 선택지로 두고(D-19 문구 그대로), '미기록으로 두고 완료' 는 작은 텍스트 버튼으로 둔다. D-18 이 허용하는 경로지만 기본 흐름은 "확인하고 넘어가기" 다. 미래·가입 전 날짜는 버튼 없이 문구만 보인다.
  - 테스트: e2e 파일 셋이 한 PostgreSQL 을 공유하고 `TRUNCATE` 를 쓰므로 jest 를 `maxWorkers: 1` 로 직렬화했다. 기존 단계 0 스위트의 `user.deleteMany()` 는 자식 행이 있으면 FK 로 실패해 TRUNCATE CASCADE 로 바꿨다(그동안은 실행 순서 덕에 통과하던 것).
- **버린 대안**: (a) 자유 끼니 '안 먹음' 저장을 웹이 `PUT /meal-records` 여러 번 + `PUT completion` 으로 — 중간 실패 시 반쯤 저장되고 업무 규칙이 Next 쪽으로 샌다(NFR-07). (b) `GET /days/{date}/completion` 만 두고 `DayDto` 에는 넣지 않기 — S-10 이 매번 두 번 요청한다. (c) 가입 전 날짜 허용 — 통계 분모(상태 전이 §4 '추적제외')가 흔들린다.
- **근거**: 완료는 통계의 유효일 기준이라 판정 함수가 하나여야 하고, 자유 끼니 확인 질문은 D-19 가 정한 대로 "막지 않되 한 번 묻는" 모양을 API 가 그대로 지원해야 한다.
- **재검토 조건**: 2주 실사용 뒤 `skipUnrecordedFree` 사용 비율을 보고 기본값을 바꿀지 판단(DEC-061 재검토 조건과 함께).

### DEC-067 개발·테스트용 로그인 `GET /auth/dev`

- 날짜 2026-11-08 / 상태 확정 / 범위: `env.ts`(`DEV_LOGIN_ENABLED`), `auth.controller.ts`, 로그인 화면 버튼(개발 빌드만), `.env.example`, `deploy/docker-compose.yml` 주석, 단위 2건·e2e 2건. 커밋: 이 항목과 같은 커밋
- **맥락**: 로그인이 카카오 하나라 로컬에서 화면을 확인할 때마다 실제 카카오 계정이 필요했고, 두 사용자 간 격리를 눌러 보려면 카카오 계정이 둘 필요했다.
- **결정**: `DEV_LOGIN_ENABLED=true` 일 때만 `GET /api/v1/auth/dev?as=<name>` 이 `dev:<name>`(기본 `tester`) 사용자를 만들거나 찾아 보통 세션 쿠키를 발급하고 `/` 로 302 한다. 꺼져 있으면 라우트가 없는 것처럼 404. `NODE_ENV=production` 에서 이 변수가 참이면 `loadEnv` 가 부팅을 거부한다. 계정 id 는 `dev:` 접두사라 숫자인 실제 카카오 id 와 겹치지 않는다. 웹 버튼은 `NODE_ENV !== 'production'` 빌드에서만 렌더한다.
- **버린 대안**: (a) 테스트용 카카오 계정 두 개 — 매번 카카오 로그인·동의를 거쳐야 하고 자동화가 안 된다. (b) JWT 를 손으로 서명해 쿠키에 넣기 — 비밀값을 사람이 다루게 된다. (c) 시드 스크립트로 사용자 행만 삽입 — 로그인(쿠키 발급)이 없으면 화면을 못 본다.
- **근거**: 인증 방식(D-07, stateless JWT)은 그대로고 발급 경로만 하나 더 있는 것이라 코드가 작다. 운영 유출은 부팅 거부로 막는 것이 문서 주의보다 확실하다.
- **재검토 조건**: 운영에서 QA 계정이 필요해지면 그때는 이 엔드포인트가 아니라 카카오 테스트 계정(DEC-015 출시 정책)으로 해결한다.

### DEC-068 통계 정의 채택과 통계 API·S-60 (단계 2 두 번째)

- 날짜 2026-11-08 / 상태 확정 / 범위: `GET /stats/summary`·`/stats/daily`(`src/stats/`), 순수 계산 `src/domain/stats.ts`, 웹 `/stats`(S-60)·하단 '통계' 탭, `components/stats/kcal-chart.tsx`, `WeightChart` 입력 타입 완화. 단위 5건·e2e 5건. 커밋: 이 항목과 같은 커밋
- **맥락**: D-20 순서의 두 번째. DEC-028(통계 정의)이 '제안' 이었고, 2026-11-08 사용자가 "제안 정의 그대로 진행" 에 동의했다.
- **결정**:
  - DEC-028 을 **확정**한다. 평균 = 하루 완료 + **그 지표가** 완전한 날만(kcal·탄·단·지 각각 따로 판정. 외식 kcal 만 입력했으면 kcal 평균에는 들어가고 탄·단·지 평균에서는 빠진다). 안 먹음은 0, 미기록은 미상. 유효일 0 이면 `null`. 미래·가입 전(사용자 시간대의 `createdAt` 날짜) 은 추적일에서 뺀다.
  - **연속 기록**은 기간과 무관하게 오늘 기준이고, 오늘을 아직 완료하지 않았으면 어제부터 센다(하루가 끝나기 전에 0 으로 보이지 않게).
  - **목표 달성일**(D-20) = 완료 + kcal 완전 + 그 날 적용되던 목표(`GoalHistory`)가 있는 날 중 `kcal ≤ dailyKcal`. 단백질 등은 1차 판정에 넣지 않는다.
  - **계획 실천율**: 분모 = 기록 당시 식단이 적용된 정규 끼니(`MealRecord.templateId` 있음, 먹었음·안 먹음, 추적일). 기록이 생길 때의 계획을 쓰므로 나중에 식단표를 바꿔도 과거 실천율이 바뀌지 않는다. 자유 끼니로 사전 변경한 끼니는 `templateId` 가 없어 분모에서 빠지고, 그 수는 `excludedByOverride`(자유 끼니 날짜 예외 수)로 따로 보인다. 분자 = 먹었음 + 내 식품 + 모든 스냅샷이 식단 품목이고 `actualQuantity = plannedQuantity`(DEC-028 미정이던 허용 오차는 **0, 정확 일치**). 미기록 끼니는 실패로 세지 않는다(기록 완료율이 따로 보여 준다).
  - 통계는 저장하지 않고 조회 시 스냅샷에서 다시 더한다. D-03 보완 뒤에는 자동으로 '영양 완전' 이 되고, 완료 뒤 수정하면(D-04 해제) 바로 빠진다. `DayCompletion.nutritionComplete` 저장값은 쓰지 않는다.
  - S-60: 기간 = 주(월~일)/월/직접 지정, 지난 같은 길이 기간과 비교 표. 일별 열량 막대는 완료한 날만 그리고 미완료일은 빈 칸(0 이 아님). 영양 불완전 날은 같은 색의 빗금 + 외곽선으로 구분하고 날짜별 표를 둔다. 다크 모드에서 두 색만으로는 색각 이상 구분 거리가 부족하다는 팔레트 검사 결과(ΔE 7.4)에 따른 것이다. 체중은 별도 차트(두 축 금지).
- **버린 대안**: (a) 지표 하나라도 미상이면 그 날 전체를 평균에서 제외 — 외식에 kcal 만 적는 흔한 경우에 kcal 평균까지 잃는다. (b) 실천율 분모를 현재 식단표로 다시 계산 — 식단표를 바꾸면 과거 실천율이 바뀐다(NFR-02 과거 불변의 취지와 어긋남). (c) 실천율 판정에 현재 식단 품목 수를 비교 — 식단을 고치면 과거 판정이 바뀐다. (d) 차트 라이브러리(Recharts) 도입 — 막대·선 둘뿐이라 SVG 로 충분하고 의존성을 늘리지 않는다.
- **한계**: 기록 시점의 식단 품목 수를 저장하지 않아 '식단 품목 하나를 빼고 먹은 끼니' 는 계획대로로 셀 수 있다. 정확히 하려면 기록 시 일치 여부를 `MealRecord` 에 저장하는 컬럼이 필요하다.
- **재검토 조건**: 실천율이 실감과 다르다는 피드백이 오면 위 컬럼(마이그레이션)과 수량 허용 오차를 검토한다. 기간이 길어 응답이 느려지면(366일 기준 쿼리 4개) 일별 집계 캐시를 검토한다.

### DEC-070 화면 어휘 — 영양 '완전·불완전·미상' 을 '확인·미확인' 으로

- 날짜 2026-11-08 / 상태 확정 / 범위: 웹 화면 문구 13개 파일(`format.ts` 의 값 표시 포함), `screens.md` 화면 어휘 대응표·§7. 코드·API·DB 이름(`nutritionComplete`, `complete`, `missing`)과 설계 문서의 도메인 용어는 그대로. 커밋: 이 항목과 같은 커밋
- **맥락**: 사용자가 "영양 완전이라는 단어가 어색하다, 영양 확인·영양 미확인은 어떤가" 를 제안했다. '완전·불완전' 은 기록을 평가하는 말처럼 들리고, 값 단위 '미상' 과 하루 단위 '불완전' 이 같은 사실(모르는 값이 있다)을 두 단어로 말하고 있었다.
- **결정**: 값 하나는 **미확인**('열량 미확인', 합계 옆 '미확인 n건'). 하루·식단 상태는 건수가 있으면 **영양 미확인 n건**, 없으면 **영양 일부 미확인**. 모두 확인된 상태는 **영양 모두 확인됨**. '영양 정보 미등록' 은 제품에 영양을 아예 넣지 않은 다른 상태라 그대로 둔다.
- **버린 대안**: (a) 사용자 제안 그대로 '영양 확인 / 영양 미확인' — '영양 확인' 은 배지에서 "영양을 확인하세요" 라는 동작으로 읽히고, 품목 하나만 모르는 날을 '영양 미확인' 이라 하면 하루 전체를 모르는 것처럼 읽힌다. (b) 하루 상태만 바꾸고 값의 '미상' 유지 — 같은 뜻에 단어가 둘이 된다.
- **근거**: "null 은 미상, 0 은 확인된 0" 불변식을 화면에서 그대로 '확인된 값 / 미확인 값' 으로 말할 수 있고, '미확인' 은 영양을 채우면 풀린다는 뜻(D-03 보완)을 담는다.
- **재검토 조건**: '미확인' 이 "사용자가 확인을 안 했다" 로 읽혀 영양 입력 대신 확인 버튼을 찾는 피드백이 나오면 '모름' 계열을 검토한다.

### DEC-072 웹 푸시 발송에 `web-push` 3.6.7(CommonJS) 고정

- 날짜 2026-11-08 / 상태 확정(구현 전) / 범위: FR-08, FR-09, NFR-05, `api.md` §11, DEC-047·049
- **맥락**: 알림(D-20 다음 순서)에 웹 푸시 발송이 필요하다. 발송 한 번에 VAPID 서명(RFC 8292, ES256 JWT)과 본문 암호화(RFC 8291, ECDH P-256 + HKDF + AES-128-GCM, RFC 8188 `aes128gcm`)가 들어간다. CLAUDE.md 규칙에 따라 node 내장(`node:crypto`)으로 되는지 먼저 봤다. 2026-11-08 기준 `web-push` 최신 4.0.0(2026-11-06 배포)은 `type: module` 인 ESM 전용이고, 3.6.7(2024-01)은 CommonJS 다.
- **선택지**: (a) `node:crypto` 로 직접 구현(DEC-049 방식, 의존성 0), (b) `web-push` 4.x, (c) `web-push` 3.6.7 고정.
- **결정**: (c). `apps/api` 에 `web-push@3.6.7`(정확한 버전) 과 `@types/web-push` 를 넣는다. VAPID 키는 `web-push generate-vapid-keys` 로 한 번 만들어 환경 변수(`env.ts` zod·`.env.example`·`deploy/docker-compose.yml`)에 두고 개인키는 로그·응답에 싣지 않는다.
- **버린 대안**: (a) 사용자가 "web-push 가 이해하기 쉽다" 로 선택. DEC-049 의 JWT 는 HS256 하나라 100줄로 끝났지만, 웹 푸시 암호화는 키 합의·키 유도·패딩·헤더 형식까지 표준 두 개를 맞춰야 하고, 브라우저(FCM·Apple·Mozilla)가 받아 주는지 실기기에서만 확인할 수 있어 검증 비용이 크다. (b) ESM 전용이라 DEC-047 의 Jest(ts-jest, CommonJS)에서 불러올 수 없고, 배포된 지 이틀 된 메이저 버전이다.
- **근거**: 3.6.7 은 오래 쓰인 안정판이고 `generateVAPIDKeys`·`sendNotification` 두 함수로 서명·암호화·발송을 감싼다. 우리 코드는 구독 저장·발송 대상 판정·응답 코드 처리(404·410 → `revoked_at`, 429·5xx → 재시도)에 집중한다.
- **영향·트레이드오프**: 런타임 의존성 1개와 그 하위 의존성(`jws`·`asn1.js`·`http_ece`·`https-proxy-agent` 7·`minimist`)이 늘어난다. 3.x 는 더 이상 갱신되지 않을 수 있다.
- **재검토 조건**: 3.6.7 이나 하위 의존성에 보안 권고가 나오면, 또는 API 를 ESM 으로 옮길 때(DEC-047 재검토) 4.x 로 올리거나 (a) 를 다시 본다.

  - 홈 화면 앱에는 새로고침이 없으므로 standalone 에서만 1분 넘게 백그라운드에 있다 돌아오면 `router.refresh()`(`ResumeRefresh`). 브라우저 탭에서는 하지 않는다.
  - 앱 이름은 화면에 쓰던 '식단 관리' 그대로(manifest `name`·`short_name`, `apple-mobile-web-app-title`).
- **버린 대안**: (a) D-20 순서 그대로 알림 먼저 — 아이폰 푸시를 시험할 수 없다. (b) 알림 단계 안에 PWA 를 섞기 — 설치·안내 화면과 구독·예약 작업이 한 커밋에 섞여 검증 범위가 흐려진다. (c) `next-pwa`·Serwist 같은 PWA 라이브러리 — 캐시 전략을 기본으로 깔아 DEC-032 와 어긋나고, 푸시만 쓰면 손으로 쓴 70줄 워커로 충분하다. (d) 아이콘을 `next/og` `ImageResponse` 로 요청 시 생성 — 한글·도형 렌더 의존이 늘고 정적 파일보다 이득이 없다.
- **검증**: `next build` 통과(`/manifest.webmanifest` 정적), 운영 빌드에서 매니페스트·아이콘 5개 200, `sw.js` 응답 헤더 확인, `<head>` 에 manifest·apple-touch-icon·`viewport-fit=cover` 확인. PC 크롬에서 서비스 워커 `activated`·페이지 제어, `beforeinstallprompt` 수신으로 S-72 '설치하기' 표시, 콘솔 오류 없음. **갤럭시 실기기(2026-11-08, 사용자)**: 크롬에서 설치 배너 → S-72 '설치하기' → 홈 화면 아이콘(마스크 잘림 없음) → standalone 실행·로그인 유지 → 하단 탭·바닥 시트가 시스템 바에 가리지 않음 → S-72 '설치됨·알림 지원' 표시, 카카오톡 인앱의 '다른 브라우저로 열기' 모두 동작. 삼성 인터넷의 '앱스에 추가'(WebAPK)는 Play 프로텍트가 설치를 막았다 — 크롬 WebAPK 는 구글이 서명해 통과하지만 삼성 인터넷은 그렇지 않다. 그래서 S-72 는 삼성 인터넷이면 설치 대화상자보다 먼저 '크롬으로 열기'(`intent://…;package=com.android.chrome`)를 권하고, 차선으로 '현재 페이지 추가 → 홈 화면'(앱스 말고)을 안내한다. Play 프로텍트를 끄라는 안내는 하지 않는다. **아이폰 실기기 확인은 아직**.
- **영향·트레이드오프**: 아이폰 홈 화면 앱은 Safari 와 쿠키 저장소가 분리돼 설치 뒤 한 번 다시 로그인해야 한다(S-72 에 안내). 카카오 OAuth 가 standalone 밖(앱 안 브라우저 시트·카카오톡 앱)으로 나갔다 돌아올 때 쿠키가 홈 화면 앱에 남는지는 미확인이고 `screens.md` §9 에 미정으로 올렸다. iOS 의 safe area 는 하단만 처리했다(가로 모드 좌우 여백은 미처리).
- **재검토 조건**: 아이폰 실기기에서 홈 화면 앱 카카오 로그인이 실패하면 알림 구현 전에 로그인 흐름(JWT 기간·갱신 포함)을 먼저 정한다. 오프라인 기록(EXT-05)을 시작하면 워커에 fetch 처리기를 넣는 결정을 따로 남긴다.

## G. 이력서·포트폴리오 활용 가이드

이 문서에서 꺼내 쓸 때의 원칙:

- **결정 → 근거 → 검증 방법** 세 가지를 한 묶음으로 인용한다. 예: "재고 이중 차감 방지를 위해 델타 API 대신 상태 설정 API와 낙관적 잠금을 선택(DEC-025), 동일 요청 2회·동시 수정 인수 시나리오로 검증."
- 버린 대안을 함께 적는다. 선택지 없는 결정은 설계가 아니라 우연이다.
- `제안` 상태 항목은 "검토한 설계"로, `확정`은 "채택한 설계"로 구분해 표현한다.
- 성능·정확도 수치는 DEC-031대로 측정 조건·표본·한계 없이 쓰지 않는다.
- 비용 제약(DEC-012)을 기술 선택의 근거로 연결하면 "제약 아래의 판단"이 드러난다.
- 구현 단계에서 결정이 바뀐 항목(`대체됨`)은 "무엇을 배워서 바꿨는가"로 서술하기 좋은 재료다.

현재 시점에서 핵심 서사가 될 수 있는 결정 묶음:

1. 정합성 설계: DEC-017, DEC-020, DEC-022, DEC-023, DEC-025
2. 데이터 정직성(틀린 숫자보다 없는 숫자): DEC-018, DEC-019, DEC-024, DEC-026, DEC-028
3. 제약 기반 인프라 선택: DEC-010, DEC-011, DEC-012, DEC-014
4. 범위·문서 통제와 AI 에이전트 협업: DEC-001, DEC-002, DEC-003, DEC-033
