## 확장 공통 요구사항

1차 문서의 NFR에서 AI·사진·크롤링에만 해당하는 항목을 옮겨 왔다.

### AI 작업 처리 (원본 NFR-03, §4)

- AI 작업은 요청 내에서 끝날 때까지 기다리지 않고 영속 작업 ID를 반환한다. API·외부 호출의 타임아웃을 별도로 설정한다. 성능 목표(p95)에서 AI 호출은 제외한다.
- 흐름: DB에 저장 후 ID 반환 → 워커 처리 → 클라이언트 상태 조회 → 사용자 확인.
- 초기 DB 작업 큐의 안전한 선점·임대 만료·재시도·중복 방지를 구현하고 Redis 도입은 필요할 때 결정한다.
- Python 워커는 AI 단계부터 도입한다. 외부 API 호출만 필요한 동안 무조건 별도 HTTP 서버를 만들 필요는 없으며, 내부 요청 인터페이스가 필요하면 FastAPI를 사용한다. 워커는 공용 인터넷에 노출하지 않는다.
- AI 제공자와 모델 호출을 교체 가능한 인터페이스로 분리한다. 업무 로직은 Node API에 두고 Python에 중복하지 않는다.
- 권고 엔터티: AnalysisJob, AIUsage, ProductSourceSnapshot.

### 사진 보관 정책 (DEC-069, 2026-11-08 확정)

저장하는 것과 버리는 것:

- 업로드 원본(스마트폰 JPEG/HEIC 3~4 MB)은 서버가 **보기용으로 리사이즈한 직후 삭제**한다. 보관 대상은 리사이즈본(긴 변 1600 px, JPEG 품질 80, 약 0.3~0.5 MB)과 썸네일(320 px, 약 30 KB)이다. AI 분석에도 리사이즈본을 보낸다(전송량·비용 감소, 분석 품질에는 충분).
- 업로드 상한: 장당 10 MB(리사이즈 전), 사용자당 하루 10장. 끼니 1건당 사진 여러 장 허용.
- 사용자는 언제든 사진을 지울 수 있고, 식사 기록을 '기록 전'으로 되돌리면 사진도 지운다. 계정 삭제 시 즉시 삭제(ops.md §6).
- 메타데이터(EXIF 위치 정보 등)는 리사이즈 때 제거한다.

보관 기간 산정(SSD 60 GB 기준):

- 디스크 배분(계획값): OS·Docker·이미지 약 8 GB, DB·로컬 백업·로그 약 4 GB, 여유 20 %(12 GB) → **사진 예산 20 GB**(20,480 MB). 디스크 사용률 80 % 초과는 어떤 경우에도 정리 트리거다.
- 유입량 = 사용자 수 × 하루 장수(계획 6장) × 장당 저장 용량. 가능한 보관 일수 = 20,480 MB ÷ 하루 유입량.

| 장당 저장 용량 | 사용자 2명 | 10명 | 30명 | 100명 | 30일 보관이 가능한 최대 사용자 | 7일 보관이 가능한 최대 사용자 |
| --- | --- | --- | --- | --- | --- | --- |
| **0.5 MB (리사이즈본+썸네일, 채택)** | 3,413일 | 683일 | 228일 | 68일 | 약 227명 | 약 975명 |
| 3.5 MB (원본 보관, 미채택) | 487일 | 97일 | 32일 | 9.7일 | 약 32명 | 약 139명 |

- 결론: 리사이즈본만 보관하면 사용자 200명까지 **30일(최대)** 을 유지할 수 있다. 원본을 보관하면 30명 선에서 30일이 깨지므로 원본은 두지 않는다.
- 규칙: `retention_days = clamp(7, 30, floor(20,480 MB ÷ 최근 14일 일평균 유입 MB))`. 매일 정리 작업이 이 값을 다시 계산해 `expires_at` 이 지난 사진을 지운다. 계산값이 30 아래로 내려가면(= 사용자 약 227명 또는 장당 용량 증가) 운영자 알림. 하한 7일에서도 예산을 넘으면 신규 업로드를 거부하고 안내한다(조용히 더 짧게 지우지 않는다).
- 사용자에게는 "사진은 최대 30일 보관되며 그 뒤 자동 삭제됩니다(기록·영양 값은 남습니다)"로 안내한다. 만료 뒤 기록에는 '사진 보관 기간 지남' 자리만 남는다.
- 권고 엔터티: `MealPhoto`(id, meal_record_id, user_id, path, bytes, width, height, created_at, expires_at, deleted_at). 파일은 VM 볼륨 `data/photos/<user_id>/<yyyy-mm>/<id>.jpg`, 응답은 API 가 접근 판정 뒤 스트리밍(서명 URL 없음, 같은 오리진·쿠키 인증 유지).
- 재검토: 사용자가 100명을 넘거나 디스크 사용률이 60 %를 넘으면 오브젝트 스토리지 이전(월 예산 DEC-012 안에서)을 검토한다.

### AI 비용 통제 (원본 NFR-06)

- 월 AI API 예산 배정 3,000원(사용자 전체 합산, 총예산 20,000원 내).
- 알림만으로 과금이 멈추지 않는다. AI는 요청 전 잔여 예산 예약, 동시 요청·재시도 비용 포함, 토큰 상한으로 제한하고 한도 도달 시 직접 입력만 제공한다. 공급자 사용 내역과 주기적으로 대조한다.
- 클라우드에서의 GPU/로컬 LLM 상시 실행은 이 예산에 포함하지 않는다. 이후 개인 장비 실험 비용과 운영 가용성을 별도 평가한다.

### 검증 (원본 NFR-07, §5)

- 핵심 테스트 추가: AI 예산 차단.
- AI 정확도를 포트폴리오에 표시할 때 측정 조건·표본·한계를 함께 남긴다.
- 인수 시나리오: 분석 중 워커 종료 → 복구 또는 실패 안내, 중복 식사 저장 없음, 보관 기간 만료 사진 삭제·원본 즉시 삭제·EXIF 제거·하루 장수 상한·디스크 80 % 트리거.

### 결정 필요

- AI 제공자·모델·호출 단가는 확장 단계 직전에 검증한다. 사진 보관 정책은 DEC-069 로 확정(7~30일, 리사이즈본만). EXT-02 분할과 순서는 DEC-071 로 확정.

## EXT-01. 영양성분표 OCR — 제품 정보 보완 단계

- [ ] 위치: 제품 상세의 ‘영양 정보 입력/수정’ → 영양성분표 촬영·업로드 → 추출 초안 → 확인·수정 → 저장.
- [ ] 구매 목록을 먼저 등록한 뒤 필요한 제품부터 사용한다. 제품 재구매에는 다시 OCR을 요구하지 않는다.
- [ ] 기준량·단위·열량·탄단지를 추출하고 총내용량과 1회분을 구분한다. ‘1g 미만’·인식 불가·누락 값을 임의의 확정값으로 바꾸지 않는다.
- [ ] 자동 저장하지 않으며 확인 전에는 재고나 기존 영양 정보를 바꾸지 않는다.
- [ ] 평가: 동의받은 라벨 표본과 정답을 마련해 필드별 정확도, 기준량 오류, 사용자 수정률, 지연, 호출 비용을 측정한다. 평가 표본을 보존하려면 운영 사진 삭제 정책과 별도로 동의를 받는다.

## EXT-02a. 식사 사진 업로드·보관 (단계 3, AI 없음)

- [ ] 위치: 식사 기록(S-11 내 식품·S-12 식단 외 식사·S-13 간식)에 '사진 추가'. 기록 1건에 여러 장. 보기는 끼니 카드 썸네일 → 전체 보기.
- [ ] 저장: 업로드 원본은 리사이즈(긴 변 1600 px·JPEG 80·EXIF 제거)·썸네일(320 px) 생성 직후 삭제. 파일은 VM 볼륨 `data/photos/<user_id>/<yyyy-mm>/<id>.jpg`, 메타는 `MealPhoto`(id, meal_record_id, user_id, path, bytes, width, height, created_at, expires_at, deleted_at). 상한 장당 10 MB(리사이즈 전)·사용자당 하루 10장. 세부는 "사진 보관 정책"(DEC-069).
- [ ] 접근: `GET /meal-photos/{id}`(소유자) 와 공유용 `GET /friends/{userId}/photos/{photoId}`(접근 판정 뒤)가 API 에서 스트리밍. 서명 URL 없음. 타인·만료는 404.
- [ ] 보관·삭제: 매일 정리 작업이 보관 일수를 `clamp(7, 30, floor(20,480 MB ÷ 최근 14일 일평균 유입))` 로 재계산해 만료분을 지운다. 기록을 '기록 전'으로 되돌리면 그 기록의 사진 삭제. 계정 삭제 시 즉시 삭제(ops.md §6). 백업 제외(DEC-014).
- [ ] 안내: 업로드 화면에 "사진은 최대 30일 보관 뒤 자동 삭제됩니다. 기록·영양 값은 남습니다". 만료 뒤 기록에 '사진 보관 기간 지남' 자리.
- [ ] 이미지 처리 라이브러리는 `apps/api` CommonJS 제약(DEC-047) 안에서 고른다(`sharp` 는 CJS 가능, 네이티브 바이너리라 Docker 이미지 크기·arm/x64 확인). 결정은 구현 시 DEC 로.
- [ ] 테스트: 타인 사진 404, 만료 사진 404·파일 없음, 원본 파일이 남지 않음, EXIF 제거, 하루 11장째 422, 기록 취소 시 사진 삭제, 정리 작업이 예산 초과 시 기간을 7일까지만 줄이고 그 아래선 업로드 거부.

## EXT-02b. 식사 사진 AI 분석 (단계 6)

- [ ] 입력은 EXT-02a 가 보관 중인 리사이즈본. 재분석은 보관 기간 안에서만 가능하고 만료 뒤에는 재업로드가 필요하다.
- [ ] 위치: 외부 식사 기록 → 사진 → 개인/공유 선택 → 메뉴·양 확인 → 저장.
- [ ] 공유 식사는 인원수 기준 1/N을 초안으로 제안할 수 있으나 실제 섭취량으로 확정하지 않는다. 개인 밥과 공유 반찬을 구분하고 메뉴별 안 먹음/양 수정 제공.
- [ ] 메뉴명만으로도 분석 가능하게 하고 사진 실패 시 직접 입력 유지.
- [ ] 결과에 ‘추정’과 기준 가정을 표시한다. 사용자 확정 시점에 실제 식사 기록으로 전환한다.
- [ ] AI 작업 상태는 대기/진행/성공/실패/취소를 관리하고, 재시도 상한·중복 저장 방지·워커 중단 복구·예산 한도를 적용한다.
- [ ] 외부 식사 알림(FR-09)에 사진 촬영 안내를 이 단계에서 추가한다.
- [ ] 평가: 메뉴 인식과 양 추정을 분리한다. 사진만으로 실제 열량 정답을 알 수 없으므로 계량·제품 정보가 있는 표본에서 오차를 검증하고 일상 사진은 수정률과 편의성을 평가한다.

## EXT-03. 제품 크롤링

- [ ] 지원 사이트의 상품 URL에서 제품명·선택 옵션·규격·가격·배송비·영양 정보·품절 여부 중 확보 가능한 값을 수집한다.
- [ ] 출처 URL·수집 시각·옵션·회원/쿠폰 조건을 저장한다. 배송비 불명 상태를 무료로 가정하지 않는다.
- [ ] 사이트 정책과 접근 가능성을 확인하고 허용된 소스부터 적용한다. 로그인 우회·차단 우회는 범위 밖이다.
- [ ] 수집 결과는 사용자 확인 후 제품에 반영한다. 실패하면 수동 입력으로 이어진다.
- [ ] 신뢰하지 않는 URL의 서버 요청은 내부 IP·메타데이터 접근 차단과 리다이렉트 재검증 등 SSRF 방어가 필요하다.

## EXT-04. 데이터 기반 LLM 추천

- [ ] 재고 소진일, 반복 식단, 목표 대비 부족분, 제품 가격·영양, 선호·조리 편의·예산으로 후보를 추천한다.
- [ ] 사례: 재구매 시점·수량, 품절 대체품, 단백질 25g당 비용, 1회 섭취 비용, 부족 영양 보완.
- [ ] 단위 변환·가격·영양 계산·필터는 코드가 수행한다. LLM은 검증된 후보 비교와 설명을 담당한다.
- [ ] 출처 없는 가격·영양·재고를 생성하지 않는다. 오래된 수집값·누락 정보·추천 근거를 표시한다.
- [ ] 크롤링 텍스트·이미지는 신뢰하지 않는 데이터로 취급한다. 그 안의 지시문으로 시스템 규칙·도구 실행을 바꾸지 않는다.
- [ ] 평가: 조건 충족률, 근거 없는 주장 비율, 대체품 적합도, 사용자 선택률, 요청당 비용을 기록한다.
