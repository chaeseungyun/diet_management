# 식단·재고·체중 관리 웹앱 — 1차 요구사항 (단계 0~2)

버전: v0.1 분리본 / 원본: [`archive/diet-app-requirements-v0.1.md`](archive/diet-app-requirements-v0.1.md) (2026-11-03) / 전달 대상: Claude Code

이 문서는 원본 요구사항 중 **1차 범위(단계 0~2)** 만 담는다. 확장 기능(OCR·사진 분석·크롤링·LLM 추천·기타)은 [`extension-todo.md`](extension-todo.md)로 분리했다.

‘확정’은 사용자와 합의한 범위, ‘제안’은 구현 기본값 또는 기술 권고, ‘미정’은 구현·결제 전에 결정할 항목이다. 기술 선택과 수치 목표를 사용자 확정 사항으로 오해하지 않는다.

## 0. 목적과 범위

### 목적

- 실익: 적은 입력으로 식사·영양·체중을 기록하고 식품 소진을 예측하여 다이어트를 지속한다. 알림과 기록 실천율로 습관을 돕는다.
- 성장: 프론트·백엔드 개발, 직접 배포·운영, 데이터 정합성, OCR·LLM 통합과 평가를 경험한다. (OCR·LLM은 확장 단계)
- 본인부터 사용하되 추후 지인이 각자 계정과 데이터로 사용한다. 개인 식단을 모든 사용자의 기본값으로 하드코딩하지 않는다.
- 개발 가능 시간은 주당 약 5시간. 작은 범위를 배포하고 실사용 피드백을 반영한다.

### 범위 경계

| 구분 | 내용 |
| --- | --- |
| 1차 범위 (이 문서) | 카카오 로그인, 수동 제품·구매·입고 등록, 반복 식단과 예외 일정, 섭취 기록, 칼로리·탄단지 계산, 체중, 재고·소진 예측, 알림, 대시보드, 직접 배포 |
| 순차 확장 | 영양성분표 OCR → 식사 사진 분석 → 제품 크롤링 → 데이터 기반 LLM 추천 → `extension-todo.md` |
| 기타 확장 | 운동 기록, 오프라인 기록·동기화, 로컬 모델 실험 → `extension-todo.md` |
| 제외·보류 | 자동 주문·결제, 쿠팡 자동 장바구니, 소비기한·개봉일 관리, 소스의 재고 차감 |

## 1. 비기능적 요구사항

### NFR-01. 사용성·접근성 [확정/제안]

- 모바일 우선으로 개발하며 PC에서는 기간별 비교와 상세 대시보드를 강화한다.
- 고정 식단은 상세 입력 없이 한 번의 ‘먹었음’ 조작으로 기록할 수 있어야 한다.
- 갤럭시를 우선 검증하고 아이폰도 지원 대상으로 둔다. 브라우저·OS·설치 상태별 PWA와 푸시 지원을 실제 기기에서 확인한다. 지원 불가 시 앱 안의 미기록 안내는 유지한다.
- PWA 설치 가능 구조를 제안한다. 오프라인 변경 기능은 1차에 포함하지 않는다.
- 제안 검증 기준: 360px 화면에서 핵심 화면의 가로 스크롤 없음, 입력 레이블·키보드 탐색·색상 외 상태 표시 제공.

### NFR-02. 데이터 정확성·정합성 [필수]

- 식사 상태 변경과 재고 변경을 하나의 DB 트랜잭션으로 처리한다.
- 같은 요청 재전송·중복 클릭·동시 요청으로 식사 또는 재고가 이중 반영되지 않아야 한다. 멱등성 키와 충돌 감지를 설계한다.
- 수량 수정·식사 취소 시 이전 차감분을 복구한 뒤 변경분만 반영한다. 재고 이동 이력을 남긴다.
- DB를 최종 상태의 기준으로 두고, 낙관적 UI가 실패하면 서버 상태로 복구한다.
- 영양 기준량, 단위, 실제 섭취량을 분리한다. ‘가루 45g’과 ‘단백질 45g’을 혼동하지 않는다.
- 입력되지 않은 값은 null/미상으로 취급한다. 0과 구분한다. 계산 중에는 정밀도를 유지하고 화면에서만 반올림한다.
- 과거 섭취 기록은 당시 제품명·섭취량·영양 정보를 스냅샷으로 보존한다. 제품·템플릿 변경으로 과거 합계가 자동 변경되지 않는다.
- 날짜 경계는 사용자 시간대를 따른다. 초기 기본값은 Asia/Seoul. 서버 UTC 저장과 로컬 식사 날짜를 명시적으로 구분한다.

### NFR-03. 성능·연결 끊김 대응 [수치는 제안]

- 로그인 사용자별 데이터가 서버 캐시를 통해 다른 사용자에게 노출되지 않아야 한다.
- 온라인 사용을 기본으로 하며 전송 실패 시 작성 내용을 보존하고 재시도할 수 있어야 한다. 미전송 상태를 저장 완료로 표시하지 않는다.
- 초기 측정 목표: 정상 부하의 일반 API p95 500ms 이내(외부 OAuth 제외), 모바일 핵심 화면 LCP 2.5초 이내. 동시 사용자 5명·사용자당 1년 기록을 시험 조건으로 삼고 기기·회선·서버 사양을 함께 기록한다.
- 성능 목표는 배포 전 기준 측정 후 조정할 수 있다. Next.js 선택 자체를 성능 보장으로 취급하지 않는다.
- 외부 호출(OAuth·푸시 등)의 타임아웃을 별도로 설정한다.
- (AI 작업 비동기 처리 요구는 `extension-todo.md` 공통 요구로 이동)

### NFR-04. 인증·개인정보·보안 [필수]

- 카카오 소셜 로그인, 서버 측 사용자별 접근 제어. 타인의 ID를 전달해도 조회·수정할 수 없어야 한다.
- OAuth state 검증, 허용된 리다이렉트, 안전한 인증 쿠키(HttpOnly/Secure 등, D-07: stateless JWT·서버 세션 없음), 요청 방식에 맞는 CSRF 방어, 로그아웃 및 토큰 만료를 처리한다.
- 최소 프로필만 수집한다. API 키·토큰·DB 비밀번호는 프론트 번들·Git·로그에 남기지 않는다.
- DB를 공용 인터넷에 직접 노출하지 않는다. 관리 접속 제한, HTTPS, 업로드 크기·형식 제한, 요청 제한을 적용한다.
- 사용자별 로컬 임시 입력은 로그아웃 시 삭제한다.
- 지인 사용 전 계정·개인 데이터 삭제 절차와 백업 만료 정책을 문서화한다.
- (사진·AI 관련 개인정보 요구는 `extension-todo.md` 공통 요구로 이동)

### NFR-05. 배포·운영·복구 [직접 운영 확정, 세부 수치 제안]

- 클라우드 VM에 Docker Compose로 웹·API·DB를 직접 운영하는 방식을 제안한다. 초기에는 고가용성·Kubernetes를 도입하지 않는다.
- CI에서 타입 검사·핵심 테스트·빌드를 실행하고, 빌드된 이미지를 배포한다. 저사양 운영 VM에서 빌드하여 서비스와 메모리를 경쟁시키지 않는다.
- 버전별 이미지, 상태 확인, 프로세스 재시작, DB 마이그레이션, 배포 실패 시 롤백 절차를 마련한다. DB 변경이 이전 앱과 호환되는지 별도로 확인한다.
- 자동 백업은 VM 외부에 암호화 보관한다. 제안: 매일 1회·7일 보관, RPO 24시간·RTO 24시간. 실제 복원 시험을 출시 전에 1회 수행한다.
- 로그 순환·디스크 사용량·메모리·API 오류·작업 실패·월 예상 비용을 관찰한다. 개인 식사 내용·토큰은 진단 로그에서 제외한다.
- 알림은 예약 작업으로 실행하고 사용자·날짜·식사·알림 유형별 중복을 방지한다. 서버 재시작 후 오래 지난 알림을 한꺼번에 보내지 않는다.

### NFR-06. 비용·도메인 [총예산 확정, 배분 제안]

- 서비스 운영 예산은 도메인 포함 월 환산 최대 20,000원이다. 개발용 Claude Code 구독·개인 PC 구매비는 별도 비용으로 가정한다.
- 연간 반복 비용 한도는 240,000원으로 관리한다. 다만 도메인은 연 단위 선결제이므로 결제 월의 실제 현금 지출은 월 환산액과 다르다. 결제 월에도 현금 20,000원 상한을 적용할지는 미정이다.

| 항목 | 월 예산 배정 | 해석 |
| --- | ---: | --- |
| 도메인 | 2,000원 | 연 24,000원 이내 목표, 등록·갱신 모두 확인 |
| VM | 12,000원 | 세금·IPv4·트래픽 등 포함한 목표 상한, 확정 견적 아님 |
| 외부 백업·저장 | 1,000원 | 실제 최소 청구액 확인 필요 |
| AI API | 3,000원 | 1차에는 미사용(확장 단계용 예약분); 사용자 전체 합산 |
| 환율·수수료·여유분 | 2,000원 | 초과를 무조건 흡수한다고 보장하지 않음 |
| 합계 | 20,000원 | 하나가 늘면 다른 항목을 줄이거나 사전 재합의 |

- 2026-11-03 확인한 Porkbun 일반 비프리미엄 .com은 등록·갱신 각각 연 $11.81. 실제 결제가는 선택 이름·환율·결제 수수료·세금 등에 따라 확인한다. 예산 환율을 임의로 1달러=1,500원으로 두면 약 17,715원/년(추가 비용 전)이다. 이는 현재 환율 인용이 아니다. 도메인 예산 24,000원은 견적이 아니라 여유를 둔 배정이다.
- 첫해 할인보다 갱신가 기준으로 선택한다. 도메인 하나와 그 하위 경로 또는 서브도메인을 활용한다. 실제 이름·등록기관은 미정이고 구매하지 않았다.
- 무료 DNS와 무료 인증서 사용을 제안한다. 유료 이메일·추가 도메인은 초기 범위 밖이다.
- VM 상품·지역·메모리는 미정이다. 2GB급을 우선 검토하되 위 VM 예산에서 구매 가능하다고 보장하지 않는다. Next·Node·DB 동시 실행을 측정하고, 예산이 맞지 않으면 공급자·구성·예산을 다시 검토한다.
- (AI 비용 차단 규칙·GPU/로컬 LLM 비용은 `extension-todo.md` 공통 요구로 이동)

### NFR-07. 유지보수·검증 [제안]

- 업무 로직은 Node API에 집중하고 웹에 중복하지 않는다. (확장 시 Python 워커에도 중복하지 않는다.)
- 핵심 테스트: 사용자 격리, 단위 변환, 재고 트랜잭션·중복 요청·복구, 날짜 예외, 과거 기록 보존, 미기록 통계 제외.
- 운영 문서: 로컬 실행, 환경 변수, 배포, 백업·복원, 도메인 갱신, 장애 대응, 비용 확인 방법.
- 성능 수치를 포트폴리오에 표시할 때 측정 조건·표본·한계를 함께 남긴다.

## 2. 기능적 요구사항

### FR-01. 계정·목표

- 카카오 로그인·로그아웃을 제공한다. 본인 1명에서 지인 다중 계정으로 확장해도 데이터가 분리되어야 한다.
- 목표 체중·일일 칼로리·단백질 목표를 직접 입력한다. 탄수화물·지방 목표 입력은 선택으로 제안한다. 첫 설정에서 목표 입력은 건너뛸 수 없다(D-20, 일일 kcal 필수).
- 목표 변경 이력을 보존하여 과거 실천 평가가 오늘의 목표로 덮이지 않게 한다. 자동 처방과 운동 칼로리 자동 가산은 하지 않는다.
- 완료 기준: 사용자 A의 데이터가 B에서 보이지 않고, 변경 목표가 지정한 날짜부터 적용된다.

### FR-02. 제품 등록 — 구매 목록 우선 방식 B

- 처음에는 구체적인 제품명·포장 규격·구매 수량을 빠르게 등록한다. 영양 정보 없이 저장 가능하다.
- 제품 정보와 구매/입고 건을 분리한다. 동일 제품 재구매 시 기존 제품을 선택하여 수량을 추가한다.
- 영양 정보는 기준량(g/ml/개/회분), 열량(kcal), 탄수화물·단백질·지방(g), 출처를 저장한다. 1회분·1팩·100g 기준을 구분한다.
- 개수↔g 변환은 실제 포장 중량이 있는 경우만 허용한다. 작은 구운란을 임의의 일반 계란 중량으로 자동 환산하지 않는다.
- 정보가 없는 제품은 ‘영양 정보 미등록’을 표시하고, 해당 제품을 쓰는 식단 합계는 불완전 표시한다.
- 제안: 영양 정보 출처는 제품 표시값/직접 입력 추정/AI 추정으로 구분(AI 추정은 확장 단계에서 사용). 표시 열량과 탄단지 환산값 차이를 이유로 제품 값을 강제 수정하지 않는다.
- 완료 기준: 프로틴 1통 1,000g에 가루 45g을 배정하면 45g 기준 영양만 계산되고, 단백질 45g으로 취급되지 않는다.

### FR-03. 구매·입고·재고

- 구매는 상품·수량·구매일·선택 가격·링크를 기록하고, 실제 ‘받았음’ 처리 시 가용 재고에 반영한다. 배송 중 재고는 분리한다.
- 기존 보유 식품은 구매 이력 없이 현재 잔량으로 초기 등록할 수 있게 제안한다.
- 닭가슴살·계란·즉석밥은 개수, 프로틴·오트밀·채소는 g 단위로 관리한다.
- 소스는 재고 차감 대상에서 제외한다. 영양 계산에는 선택적으로 기본 추정 섭취량을 포함한다. 매번 계량을 요구하지 않는다.
- 폐기·다른 용도 소비·실측 잔량 보정을 수동 반영하고 사유와 변경량을 기록한다.
- 제안: 재고가 부족해도 실제 먹은 기록을 막지 않는다. 원장상 부족분을 드러내고 ‘재고 확인 필요’로 표시한다. 음수를 조용히 0으로 잘라 정보가 사라지게 하지 않는다.
- 완료 기준: 30팩 입고 후 2팩 섭취 체크 시 28팩, 취소 시 30팩, 동일 요청 재시도에도 28팩이다.

### FR-04. 반복 식단·일정 예외

- 아침·점심·저녁·오후 간식·저녁 간식 슬롯을 제공한다. 슬롯별 제품과 수량을 묶어 식단을 만든다.
- 요일별 반복 + 특정 날짜/기간 변경을 지원한다. 슬롯은 식단(템플릿)/자유 끼니(계획 없음, D-18) 둘로만 구분한다. '외부 식사 예정' 계획 유형은 두지 않는다(D-19).
- 출장 기간은 자유 끼니로 일괄 변경하고 특정 슬롯은 기존 식단 유지 가능하다. 기간 종료 후 반복 계획으로 복귀한다.
- 날짜 예외가 반복 계획보다 우선하며 계획 변경은 이미 확정한 섭취 기록을 수정하지 않는다.
- 자유 끼니는 허용된 끼니다. 자유 끼니라는 이유로 실패로 표시하지 않는다. 미기록 영양을 추측해서 채우지 않는다.
- 완료 기준: 3일 출장으로 저녁만 자유 끼니로 바꾸면 해당 3일의 닭가슴살 예상 사용량만 줄어든다.

### FR-05. 실제 섭취 기록

- 상태는 미기록/먹었음/안 먹음 세 가지다. ‘다르게 먹음’은 상태가 아니라 내용 수정·외부 식사로 변경하는 동작이다.
- 계획 그대로 먹기, 일부 수량 변경, 음식 추가, 외부 식사로 대체, 취소·과거 기록 수정을 지원한다.
- 외부 식사(`kind=outside`, 화면 문구 **식단 외 식사**: 배달·외식·본가 집밥처럼 집 제품을 쓰지 않은 식사, D-19)는 집 제품 재고를 차감하지 않는다. 예외적으로 집 제품을 추가했다면 해당 항목만 차감한다.
- 1차 외부 식사 입력: 메뉴명과 직접 입력한 영양 추정값. 메뉴명만 저장할 수 있지만 영양 미상으로 표시한다. AI 이전에 메뉴명으로 자동 영양 계산이 되는 것처럼 구현하지 않는다.
- 예정량·실제량을 분리한다. 먹었음 체크 전에는 실제 영양 합계나 재고를 변경하지 않는다.
- 완료 기준: 예정 닭가슴살 200g을 실제 100g으로 바꾸면 영양과 재고 모두 100g에 해당하는 값만 반영된다.

### FR-06. 하루 완료·통계 정의

- 제안 기본 규칙: 활성화된 당일 식사 슬롯이 모두 먹었음/안 먹음이고 사용자가 ‘하루 완료’를 누르면 기록 완료로 처리한다. 추가 간식 입력은 별도 지원한다.
- 하루 기록 완료와 영양 계산 완료는 구분한다. 먹은 식사의 영양이 누락됐다면 ‘기록 완료·영양 불완전’이다.
- 일일 화면은 기록된 영양 합계, 예상 계획 합계, 미기록 슬롯, 영양 누락을 구분한다.
- 주간·월간 평균은 하루 기록과 해당 영양 지표가 모두 완전한 날만 포함한다. 유효일 수/전체일 수와 제외 이유를 함께 표시한다. 불완전한 주간 합계는 ‘기록된 합계’로 명시한다.
- 확인된 안 먹음은 섭취 0, 미기록은 미상이다. 유효일 0일이면 평균은 0이 아니라 데이터 없음이다.
- 주간 기록 완료율 = 완료한 날짜 수 / 추적 대상 날짜 수. 미래 날짜와 가입 전 날짜는 제외한다.
- 연속 기록은 체중 감소나 고정 식단 준수 여부가 아니라 하루 기록 완료에 기반한다.
- 계획 식단 실천율의 제안 정의: 고정 식단 대상 슬롯 중 계획대로 섭취한 슬롯 비율. 자유 끼니로 사전 변경한 출장 등은 분모에서 제외. 계획 변경 시점을 남기고 기록 완료율과 별도 표시한다. 세부 수량 허용 오차는 미정이며 1차에는 정확 일치로 제안한다.
- 완료 기준: 점심 미기록 날을 0kcal로 포함하지 않는다. 외식 영양 미상 날도 완전한 일일 열량 평균에서 제외한다.

### FR-07. 체중·대시보드

- 날짜별 체중 입력·수정·삭제. 제안: 하루 대표 기록 1개, 필요 시 덮어쓰기 확인.
- 실제 측정값, 주간·월간 변화, 목표까지 차이, 최근 7일 실제 측정값 평균을 제공한다. 미측정일은 0으로 채우지 않고 평균에 사용한 측정 횟수를 표시한다.
- 모바일: 오늘 식사, 목표 대비 섭취량, 다음 식사, 구매 예정. PC: 기간별 영양·체중·기록률·계획 실천율.
- 체중만으로 정확한 체지방 감소나 목표 도달일을 확정하지 않는다. 자동 도달일 예측은 1차 필수가 아니다.
- 완료 기준: 7일 중 3회 측정했으면 3회 평균으로 표시하고 체중과 지방량을 동일시하지 않는다.

### FR-08. 소진 예측·구매 알림

- 현재 재고와 미래 계획별 소비량을 순차 계산하여 다음 식사를 충족하지 못하는 날짜를 예측한다.
- 날짜 예외·입고·실제 소비량 변경·수동 보정 시 재계산한다. 오늘 이미 먹은 양을 예정량에서 다시 차감하지 않는다.
- 미기록 과거 식사를 실제 소비로 단정하지 않는다. 재고 추정 신뢰도가 낮을 수 있음을 안내하고 잔량 확인을 제공한다.
- 제안 기본값: 소진 3일 전 알림, 사용자 변경 가능. 구매 링크를 열 수 있고 주문·장바구니 자동화는 하지 않는다.
- 계획이 없거나 소비량이 0이면 ‘예측 불가/예정 소비 없음’. 배송 중 상품은 확정 재고로 합산하지 않는다.
- 완료 기준: 구매 단위·섭취 단위가 다르더라도 변환값에 따라 계산되고, 출장 일정이 추가되면 소진일이 뒤로 이동한다.

### FR-09. 알림

- 다섯 식사 슬롯별 알림 on/off와 시각을 설정한다. 초기에는 사용자가 명시적으로 허용한 슬롯만 발송한다.
- 식단 끼니는 섭취 체크 안내를 제공한다. 자유 끼니에는 슬롯 알림을 보내지 않는다(D-19. '외부 식사 사전 메뉴 기록 안내'는 폐기). 사진 분석 구현 전에는 지원하지 않는 촬영·분석 화면으로 유도하지 않는다.
- 제안: 미기록 재알림은 1회·60분 후 기본값. 하루 마감 알림(미기록 자유 끼니 확인 포함)은 단계 2에서 검토한다. 모두 조정 가능한 설정으로 취급한다.
- 먹었음/안 먹음 처리 후 추가 미기록 알림을 중지한다. 권한 거부·푸시 실패 시 앱의 미기록 표시로 대체한다.
- 시간대와 기간 예외를 반영하고 재시도 중복 발송을 방지한다. 푸시 도착 시각을 보장한다고 표현하지 않는다.

## 6. 설계 결정 [사용자 확정]

검토 과정에서 드러난 모호점 중 사용자가 확정한 항목. FR 본문과 충돌하면 이 절이 우선한다. D-01~D-04는 2026-11-03, D-05~D-15는 2026-11-05, D-16·D-17은 2026-11-06, D-21·D-22는 2026-11-08 확정.

### D-01. 계획 식사는 그때그때 계산한다

- `MealRecord`는 사용자가 식사를 체크·수정할 때만 생성한다. 미래 날짜의 레코드를 미리 만들지 않는다.
- ‘오늘 예정 식사’는 `WeeklySchedule` + `DateOverride`에서 계산한다. 소진 예측(FR-08)도 같은 계산 함수를 사용한다.
- 미기록 판정 = 예정 슬롯이 있는데 해당 날짜·슬롯의 `MealRecord`가 없거나 상태가 미기록. 알림(FR-09)과 통계(FR-06)는 이 정의를 따른다.
- 계획 변경은 레코드가 없는 미래에만 영향을 주므로 FR-04 “확정 기록을 수정하지 않는다”가 자연히 충족된다.

### D-02. 재고는 제품별 재고 단위로, 소수 허용

- 제품마다 **재고 단위**(팩/개/g/ml)를 두고, 선택적으로 **단위 중량**(예: 1팩 = 100g)을 둔다.
- 섭취 입력은 재고 단위 또는 g(단위 중량이 있을 때만) 중 선택한다. 단위 중량이 없는 제품은 g 입력을 비활성화한다(FR-02 임의 환산 금지 유지).
- 100g 섭취 시 0.5팩을 차감한다. 재고·섭취 수량 컬럼은 `decimal`이다. 화면에는 “0.5팩 (50g)”처럼 병기한다.
- 프로틴·오트밀처럼 g로 관리하는 제품은 재고 단위 = g, 단위 중량 없음으로 같은 모델에 들어간다.

### D-03. 영양 미상 스냅샷은 사용자 확인 후 보완 가능

- 제품에 영양 정보를 처음 입력(또는 수정)할 때 해당 제품의 **영양 미상** `MealItemSnapshot`이 있으면 건수를 보여 주고 적용 여부를 묻는다.
- 적용 시 미상 스냅샷만 채운다. 이미 값이 있는 스냅샷은 변경하지 않는다(NFR-02 유지).
- 보완된 스냅샷에는 출처 ‘사후 보완’과 보완 시각을 남겨 원래 스냅샷과 구분한다.
- 보완으로 해당 날짜의 ‘영양 불완전’이 해소되면 통계 유효일에 포함된다.

### D-04. 식사 상태 전이와 ‘취소’

- 상태는 미기록/먹었음/안 먹음 세 가지. 어느 상태에서 어느 상태로든 직접 전이할 수 있다(3×3 전부 허용). 먹었음 → 먹었음은 수량·내용 수정이다.
- UI의 ‘취소’는 **미기록으로 설정**하는 요청이다. 재고를 복구하고 미기록 알림을 재개한다. 인수 시나리오 3의 “취소 → 30팩”과 일치한다.
- 하루 완료(`DayCompletion`) 상태에서 취소·수정이 일어나면 완료를 해제한다.

```
   [미기록] ──먹었음 체크──▶ [먹었음] ──수량·내용 수정──▶ [먹었음]
      ▲  │                     │  ▲
      │  └──안 먹음───▶ [안 먹음]│  │
      │                  │     │  │
      └───── 취소(=미기록 설정) ─┴──┘   (어느 상태에서든 가능)
   재고 이동 = f(이전 상태·수량, 새 상태·수량). 외부 식사 항목은 이동 0.
```

- API는 델타가 아니라 **상태 설정** 방식이다: `PUT /meal-records/{date}/{slot}` 에 `{status, items[], version}`. 서버가 이전 스냅샷과의 차이로 `StockMovement`를 만든다. 같은 요청의 재전송은 차이가 0이라 무해하고, `version` 불일치는 409로 거부한다. 멱등성 키(NFR-02)는 순서가 뒤바뀐 재전송을 막는 보조 수단이다.

### D-05. 기술 스택과 리포지터리 구조 [2026-11-05]

- §3 권고안을 확정한다: Next.js + TypeScript(웹·PWA), NestJS + TypeScript(인증·모든 업무 규칙), PostgreSQL.
- pnpm 모노레포: `apps/web`(Next), `apps/api`(Nest), `packages/shared`(공유 타입·상수·enum). ORM은 Prisma.
- NestJS Swagger로 OpenAPI 문서를 생성하고 프런트의 API 타입은 그 산출물에서 생성한다. DTO를 프런트에 손으로 중복 정의하지 않는다.

### D-06. 타인 리소스 요청은 404 [2026-11-05]

- 세션 사용자 소유가 아닌 리소스 ID로 조회·수정·삭제를 요청하면 존재 여부와 관계없이 `404`를 돌려준다. `403`은 쓰지 않는다.
- 근거: 리소스 존재 여부 자체가 개인정보이므로 노출하지 않는다. 격리 테스트(시나리오 7)는 `404`를 단언한다.
- 화면(G-03)은 ‘권한 없음’이 아니라 ‘찾을 수 없음’으로 표시한다.

### D-07. 인증은 stateless JWT + HttpOnly 쿠키 [2026-11-05]

- 서버는 세션 저장소(DB 세션 테이블·Redis)를 두지 않는다. 카카오 콜백 성공 후 서버가 서명한 JWT를 HttpOnly·Secure·SameSite 쿠키로 발급하고, 모든 요청은 그 토큰의 사용자로 범위를 강제한다.
- 로그아웃은 쿠키 삭제다. 만료는 토큰 `exp`로 처리한다. 만료 전 토큰을 서버에서 강제 무효화하는 기능은 1차 범위 밖이다.
- 개발 중 카카오 리다이렉트 URI는 `localhost`를 등록한다. 출시 대상 계정 정책·검수는 도메인 확정 후 정한다.
- 토큰 만료 기간·갱신 방식과 CSRF 세부(SameSite 값, Origin 검사)는 §7-6 미정.

### D-08. 식사 기록의 낙관적 잠금은 정수 `version` [2026-11-05]

- `MealRecord`에 정수 `version` 컬럼을 두고 쓰기마다 1 증가한다. `PUT /meal-records/{date}/{slot}`의 `version`은 이 값이며 불일치는 `409`(D-04).
- `updated_at` 비교는 쓰지 않는다. 레코드가 없는 슬롯은 `version=null`로 조회되고 첫 저장에서 0부터 시작한다.
- 1차에서 낙관적 잠금은 식사 기록에만 적용한다.

### D-09. 소스는 제품 플래그로 모델링 [2026-11-05]

- 소스는 별도 제품 유형이 아니라 `Product.is_stock_tracked=false` 플래그다. 재고 원장에 기록하지 않고 소진 예측에서 ‘예측 불가’다.
- 선택적 `default_serving_amount`를 두고, 이 값으로 계산한 영양의 출처는 `manual_estimate`(직접 입력 추정)로 표시한다.
- 플래그는 사용자가 바꿀 수 있으며 과거 스냅샷·원장은 영향을 받지 않는다.

### D-10. 추가 간식(`extra`)은 id로 식별 [2026-11-05]

- 정규 5슬롯은 (user, meal_date, slot) 유니크. `extra`는 같은 날 여러 건을 허용하고 `id`로 식별한다.
- 경로는 `POST /meal-records/{date}/extra`, `PUT|DELETE /meal-records/{date}/extra/{id}`. 삭제는 차감 전량을 복구한다.
- `extra`는 하루 완료의 활성 슬롯 판정에 포함하지 않고(추가 입력), 영양 합계·영양 완전 판정에는 포함한다.

### D-11. 제품 단위 모델: 표시 단위·포장당 재고 단위·영양 기준 단위 [2026-11-05]

- `Product.stock_unit`(g/ml/ea)은 계산 단위다. `ea`인 제품은 **표시 단위명** `unit_label`(팩·개·통·장 등)을 필수로 두고 화면은 “0.5팩 (50g)”처럼 표시한다. g/ml 제품은 `unit_label`이 없다.
- **포장 1개 = 재고 단위 N**을 `Product.units_per_package`로 저장한다. 입고 수량 기본값 = 구매 수량 × N이며 받았음 처리 시 수정할 수 있다. 예: 프로틴 1통 = 1000(g), 닭가슴살 1팩 = 1(ea), 계란 1판 = 30(ea). 기존 `package_amount`·`package_unit`은 제거한다.
- `pack_weight_g`는 **ea 1단위의 g**로 ea↔g 변환 전용이다(D-02 유지).
- 영양 기준 단위 `ProductNutritionVersion.basis_unit`은 g/ml/ea만 허용하고 `serving`을 없앤다. 기준 단위는 제품의 `stock_unit`과 같거나, `pack_weight_g`가 있는 ea 제품에 한해 g일 수 있다. 그 외 조합은 저장을 거부한다(422). “1회분” 기준은 기준량을 재고 단위 수량(예: 30g)으로 적어 표현한다. FR-02의 “(g/ml/개/회분)”은 이 규칙으로 읽는다.
- `MealTemplateItem.unit`·`MealItemSnapshot.unit`도 g/ml/ea만 허용한다(D-02 입력 규칙과 일치).
- 소스의 `default_serving_amount`는 `stock_unit` 기준 수량이다.

### D-12. 알림 중복 방지 유니크와 취소 후 재개 방식 [2026-11-05]

- `NotificationDelivery`의 유니크 (user, type, target_date, slot, product_id)는 NULL을 같은 값으로 취급한다(PostgreSQL `UNIQUE NULLS NOT DISTINCT`, 원시 SQL 마이그레이션). 식사 알림은 `product_id`가, 소진 알림은 `slot`이 NULL이므로 기본 유니크로는 중복을 막지 못한다.
- 식사가 `eaten|skipped`가 되면 같은 식사의 pending 행을 `skipped`로 바꾼다. 취소로 `unrecorded`가 되면 **새 행을 만들지 않고** 그 `skipped` 행을 `pending`으로 되돌리고 `scheduled_at`을 재계산한다. 이미 `sent`인 행은 다시 보내지 않는다.

### D-13. 원장 이동이 있는 제품의 `stock_unit` 변경 금지 [2026-11-05]

- `StockMovement`가 1건이라도 있으면 `stock_unit` 변경을 422로 거부한다. 단위가 섞이면 `SUM(delta)`가 무의미해진다.
- `unit_label`·`units_per_package`·`pack_weight_g`·`is_stock_tracked`·`default_serving_amount`는 언제든 변경 가능하며 미래 계산에만 영향을 준다.

### D-14. 카카오 콜백은 API가 받고, 웹·API는 같은 오리진 [2026-11-05]

- 카카오에 등록하는 리다이렉트 URI는 API 경로(`/api/v1/auth/kakao/callback`)다. API가 state 검증·`User` upsert·JWT 쿠키 발급(D-07)을 마치고 웹 `/`로 302 한다. 실패는 `/login?error=1`로 302 하며 사유를 싣지 않는다.
- 웹의 “로그인 처리 중” 화면(S-02)은 두지 않는다.
- 웹과 API는 **같은 오리진**이다. 운영은 Caddy가 `/api/*`를 NestJS로, 나머지를 Next로 보낸다. 개발은 Next rewrite로 `/api/*`를 NestJS 포트로 보낸다. CORS 설정과 쿠키 도메인 지정이 필요 없다.

### D-15. 재고 원장 쓰기는 단계 1, 재고 화면·예측·보정은 단계 2 [2026-11-05]

- 단계 1: 구매·입고(`Purchase`, `StockReceipt`), 초기 잔량 등록, 식사 기록의 `consume`/`consume_reverse` 이동. 식사 상태와 재고 변경이 한 트랜잭션이어야 하므로(NFR-02) 기록 기능과 함께 만든다. 인수 시나리오 3·4는 단계 1에서 API 테스트로 검증한다.
- 단계 2: 재고 현황·원장 화면(S-40~S-42), 소진 예측, 수동 보정·폐기, 소진 알림.
- §4 표의 단계 1·2 완료 조건을 이에 맞춘다.

### D-16. D-03 보완 흐름은 2단계(저장 응답 건수 + `backfill` 호출) [2026-11-06]

- `POST /products/{id}/nutrition` 응답에 영양 미상 스냅샷 건수(`unknownSnapshotCount`)를 싣고, 화면(S-33)이 확인 다이얼로그를 띄운 뒤 사용자가 동의하면 `POST /products/{id}/nutrition/backfill`을 호출한다.
- 저장과 보완을 분리하므로 영양 저장이 보완 질문에 막히지 않고, 보완은 언제든 다시 호출할 수 있는 멱등 작업이다. 값이 있는 스냅샷은 건드리지 않는다(D-03).
- 2026-11-06 사용자가 Claude Code 권고에 위임해 확정. 권고의 근거는 [`api.md`](api.md) §12-7과 S-33 확인 다이얼로그와의 일치.

### D-17. 단계 1 구현에서 채택한 §7-7 기본값 [2026-11-06]

- §7-7의 권고 기본값을 그대로 구현했다(사용자가 "권고대로" 위임): `plan_changed`는 레코드 생성 시 계획이 `DateOverride`에서 왔으면 true, `skipped`는 품목 스냅샷 없이 섭취 0·영양 완전, `MealRecord.kind`는 `home|outside`, 같은 멱등성 키의 동시 요청은 첫 트랜잭션이 끝날 때까지 대기 후 저장 응답, 생성 경쟁의 유니크 위반은 409, `weekday`는 ISO 1=월~7=일, 참조 중인 템플릿·제품 보관은 422, 자식 테이블에 `user_id` 없음. 세부는 [`decisions.md`](decisions.md) DEC-055.
- 동시 수정의 version 검사는 "조회 후 비교"가 아니라 **version 조건부 갱신(행 잠금)** 으로 한다. 같은 version 으로 동시에 쓰면 먼저 커밋한 쪽만 통과하고 나머지는 409 (D-08 보강).

### D-18. '계획 없음' 슬롯은 자유 끼니, 쓰는 끼니는 사용자 설정 [2026-11-07]

- 계획 유형 `none`의 뜻은 "식단에 포함하지 않는 끼니"다. 화면 문구는 **자유 끼니**. 먹었으면 기록하고, 안 먹었으면 아무것도 하지 않는다. 원래 안 먹는 끼니를 따로 구분하는 유형(`skip`)은 만들지 않는다.
- 집계 규칙: **미기록 자유 끼니만** 하루 완료·통계·예상 영양에서 제외한다. 먹었음·안 먹음으로 기록한 자유 끼니는 다른 슬롯과 같이 집계한다(§7-2 종결, 제안 "미포함"과 같음). 미기록 자유 끼니는 '미상'이 아니라 '집계 대상 아님'이다.
- 사용자는 **쓰는 끼니**(`User.active_slots`, 1개 이상, 기본 5개 전부)를 고른다. 고르지 않은 끼니는 오늘 화면·주간 격자·캘린더에 보이지 않지만, 기록이 있는 날에는 보인다(과거 기록 보존). 첫 설정(S-03)과 설정(S-70)에서 바꾼다.
- 오늘 화면은 미기록 자유 끼니를 한 줄로 접어 보여 준다. 다음 식사(nextSlot)·완료 판정은 자유 끼니를 건너뛴다.
- 날짜 예외는 캘린더뿐 아니라 **해당 날짜·끼니 화면(S-11)에서 "이 날은 다르게 먹을 예정"** 으로 만들 수 있다. 범위는 D-19에서 **식단 끼니의 미래 날짜**로 좁혔다(자유 끼니에는 버튼 없음). 데이터는 그대로 `DateOverride`(D-01).
- 2026-11-07 사용자가 Claude Code 권고안("1번·2번 권고안대로")을 확정. 기록: [`decisions.md`](decisions.md) DEC-059.

### D-19. 계획 유형은 식단/자유 끼니 둘뿐, 기록 종류 '식단 외 식사', 완료는 '쓰는 끼니에 미기록 없음' [2026-11-07]

- 계획 유형 `outside`('외부 식사 예정')를 없앤다. `PlanType = template | none`. 기존 식단표의 `outside` 칸은 삭제(=자유 끼니), 날짜 예외의 `outside`는 `none`으로 이전한다.
- 이유: 배달·본가 집밥처럼 "외부"가 장소를 묻는 것처럼 읽혀 계획 단계에서 애매하고, 기록 단계에서는 외부 식사 예정과 자유 끼니가 이미 같은 흐름이었다.
- 기록 종류 `MealRecord.kind`는 `home|outside` 그대로 둔다. 화면 문구는 `home`=**내 식품**, `outside`=**식단 외 식사**(배달·외식·본가 집밥처럼 내 식품을 안 쓴 식사. 메뉴명·영양 직접 입력, 재고 차감 없음, 곁들인 내 식품만 차감).
- **하루 완료** = 쓰는 끼니 중 식단 끼니에 미기록이 없는 상태. 자유 끼니는 미기록이어도 완료를 막지 않고, 기록하면 집계에 들어간다(D-18). 완료는 **목표 달성과 분리**한다(달성은 별도 지표, D-20). 단계 2의 완료 다이얼로그에서 미기록 자유 끼니를 한 번 확인한다("뭔가 드셨나요? 아니오 / 기록", 아니오 = 안 먹음으로 저장).
- 알림: 자유 끼니에는 슬롯 알림을 보내지 않는다. `outside_pre`(외부 식사 사전 알림) 유형은 폐기. 하루 마감 알림은 단계 2에서 검토.
- S-11의 날짜 예외 버튼은 **식단 끼니의 미래 날짜**에서만 보인다. 자유 끼니의 미래 계획은 캘린더(S-23)가 맡는다.
- 받아들인 불이익: 외식 예정 끼니를 빼먹어도 완료가 막히지 않는다(확인 질문으로 보완). 슬롯 알림 하나가 줄어든다. "식단 없이도 기록을 강제하고 싶은 끼니"가 필요해지면 슬롯별 '기록 필수' 플래그를 재검토한다.
- 2026-11-07 사용자 확정("외부 식사 예정과 자유 끼니는 합치자"). 기록: [`decisions.md`](decisions.md) DEC-061.

### D-20. 기록 화면 원칙 — 미기록은 선택지가 아니다, 완료와 목표 달성 분리, 목표 kcal 필수, 단계 2 순서 [2026-11-07]

- 제품 정체성: **정해진 식단을 먹는 다이어터의 기록 앱**. 식단표와 재고는 입력을 없애기 위한 수단이고 목적은 체중·섭취 관리다.
- S-11 상태 선택은 **먹었음 / 안 먹음** 두 버튼. 미기록은 사용자가 고르는 상태가 아니라 기록이 없는 기본값이므로 선택지에서 빼고, 기록이 있을 때만 "기록 취소"(기록 전으로 되돌리고 뺐던 양을 복구) 보조 동작으로 둔다. 데이터 상태 3개와 3×3 전이(D-04)는 그대로다.
- S-11은 한 경로·두 모드(기록 전 / 기록 후). 식단 끼니의 먹었음은 계획 그대로 즉시 저장하고 '다르게 먹었음'은 보조 버튼. 자유 끼니의 먹었음은 **식단에서 고르기 / 내 식품 직접 고르기 / 식단 외 식사** 세 갈래이며 기록만 남기고 식단표·날짜 예외는 건드리지 않는다.
- S-10: 자유 끼니 카드에도 식단 끼니와 같은 크기의 '먹었음' 버튼을 두고, 식사 섹션에 "+ 식사 추가"(미기록 자유 끼니·설정에서 숨긴 끼니·간식)를 둔다.
- 목표(FR-01): 일일 kcal **필수**, 단백질 권장, 탄·지 선택. 오늘 요약에 목표 대비(목표 내 / 초과), 통계에 목표 달성일 x/y(완료일 기준)를 별도 지표로 보인다.
- 단계 2 순서: 하루 완료(자유 끼니 확인 포함) → 통계(완료일 평균 섭취 vs 체중 추세, 목표 달성일) → 알림 → 재고 화면·소진 예측·보정 → PWA.
- 2026-11-07 사용자 확정. 기록: [`decisions.md`](decisions.md) DEC-061. 구현은 단계 1 마무리 커밋들에서 순서대로 진행한다.

### D-21. 음수 재고는 '재고 확인 필요'로 표시하고 소진 예측·소진 알림에서 제외 [2026-11-08]

- 원장 합계가 음수인 제품은 S-40·S-32·S-10 ⑦에서 수준 배지 **재고 확인 필요**(`stockCheckNeeded=true`)로 보이고, 소진 예정일은 계산하지 않는다(`depletionDate=null`). 음수를 '이미 소진' 또는 '0' 으로 바꿔 보이지 않는다.
- 음수 상태에서는 소진 알림(FR-08)을 만들지 않는다. 사용자가 실측 잔량 보정(S-42) 또는 입고로 0 이상으로 되돌리면 그때부터 다시 예측·알림한다.
- 재고 수치 자체는 음수 그대로 노출한다(FR-03, `GET /stock` 규칙 유지). 데이터 구조 변화는 없고 표시·알림 규칙만 정한 것이다.
- 2026-11-08 사용자 확정. 기록: [`decisions.md`](decisions.md) DEC-063.

### D-22. 소진 알림과 식사 알림은 한 체계 [2026-11-08]

- 식사 알림(FR-09)과 소진 알림(FR-08)은 같은 `NotificationSetting`·`NotificationDelivery`·예약 작업·푸시 발송 코드를 쓰고 `type`/`kind` 값으로만 구분한다. 설정 화면은 S-71 하나(식사 알림 묶음 + 소진 알림 묶음).
- 식사 행은 (날짜, 슬롯), 소진 행은 (날짜, 제품)으로 식별한다. 중복 방지 유니크는 하나다(D-12). 재시작 뒤 몰아 보내지 않음·실패 기록·구독 관리는 한 번만 구현한다.
- D-12의 `NULLS NOT DISTINCT`는 DEC-055(원시 SQL 금지)와 충돌하므로 단계 2 알림 구현 시 `slot`·`product_id`에 센티널 값을 두는 방식으로 대신한다. 데이터 모델은 ERD 전제 A4 그대로다.
- 2026-11-08 사용자 확정. 기록: [`decisions.md`](decisions.md) DEC-064.

1. ~~**소스 제품의 모델링**~~ → D-09로 확정(플래그, 출처 `manual_estimate`).
2. ~~**슬롯 ‘계획 없음’의 완료 조건**~~ → D-18로 확정(자유 끼니. 미기록이면 제외, 기록했으면 포함).
3. ~~**재고 원장 음수와 소진 예측**~~ → D-21로 확정(‘재고 확인 필요’ 배지, 예측·소진 알림 제외).
4. ~~**구매 알림의 전달 경로**~~ → D-22로 확정(한 체계, 알림 유형으로 구분).
5. **VM 메모리**: Next.js와 NestJS 두 Node 프로세스 + PostgreSQL을 2GB VM에서 운영하는 것은 빠듯할 수 있다. 단계 0에서 실측을 우선하고, 부족 시 Next 정적 내보내기 등 대안을 검토한다.
6. **JWT 만료·갱신·CSRF 세부**(D-07): 액세스 토큰 만료 기간, 갱신 토큰 도입 여부(없으면 만료 시 재로그인), SameSite 값과 Origin 검사 방식. 제안: 만료 7일·갱신 토큰 없음·SameSite=Lax + Origin 검사. 단계 0 코드는 이 제안을 기본값으로 구현했다(DEC-051). 사용자 확정은 아직이다.
7. **정합성 검토(2026-11-05)에서 발견한 정의 누락** (결정 전까지 괄호의 권고를 기본값으로 둔다):
   - `MealRecord.plan_changed`의 ‘사전’ 기준 (권고: 레코드 생성 시 적용 계획이 `DateOverride`에서 왔으면 true).
   - `skipped` 상태의 스냅샷 (권고: 품목 스냅샷을 만들지 않고 섭취 0·영양 완전으로 취급).
   - `MealRecord.kind` template|outside에 ‘계획 없음 슬롯에서 집 제품을 먹음’의 자리 (권고: `home|outside`로 개명).
   - 같은 멱등성 키의 동시 요청 처리 (권고: 키 행 잠금으로 첫 요청 완료까지 대기 후 저장된 응답 반환).
   - `version=null` 생성 요청의 동시 충돌 (권고: 유니크 위반을 409로 매핑).
   - `weekday` 0의 의미 (권고: ISO, 1=월 ~ 7=일로 바꾸고 0 사용 안 함).
   - 알림이 꺼진 슬롯의 ‘지난 슬롯’ 기준 시각 (권고: 슬롯별 기본 시각 상수, 설정 시각이 있으면 그것).
   - 템플릿·제품 보관 시 참조 중인 주간 계획·템플릿 품목 처리 (권고: 참조가 있으면 보관 거부 422).
   - 온보딩 완료 표시 (권고: `User.onboarded_at` 컬럼).
   - 소진 예측에서 오늘 `skipped` 슬롯 (권고: `eaten`과 같이 건너뜀).
   - 자식 테이블(`MealItemSnapshot`·`MealTemplateItem`·`ProductNutritionVersion`)의 `user_id` (권고: 두지 않고 부모 조인으로 격리, CLAUDE.md 불변식 문구 수정).
