# 공공데이터 기반 음식 DB 구축 계획 [제안]

작성 2026-11-06. 상태: **제안** (데이터셋·라이선스·단계 배치는 사용자 결정 대기, [`decisions.md`](decisions.md) DEC-058 · §F).

## 1. 목적과 범위

제품 등록 때 영양 성분을 손으로 옮겨 적는 부담을 줄인다. 사용자가 제품명으로 검색해 공공 DB 항목을 **직접 고르면** 영양 값을 채워 준다. 고르지 않으면 지금처럼 수동 입력이다.

하지 않는 것:

- 메뉴명만으로 외부 식사 영양을 자동 계산하지 않는다(FR-05, "틀린 숫자보다 없는 숫자"). 외부 식사 입력(S-12)에서도 사용자가 항목을 명시적으로 선택했을 때만 값을 복사한다.
- 공공 DB 항목을 사용자 제품으로 자동 등록하지 않는다. 샘플·공공 데이터는 사용자 데이터가 아니다(CLAUDE.md 저장소 관례).
- 크롤링·OCR·LLM 추정은 별도 확장(EXT-01~03, [`extension-todo.md`](extension-todo.md)).

## 2. 후보 데이터셋 (확인 필요)

| 후보 | 제공처 | 특징 | 확인할 것 |
| --- | --- | --- | --- |
| 식품영양성분 데이터베이스 | 식품의약품안전처, 공공데이터포털(data.go.kr) | 가공식품·원재료성 식품·음식(조리식품) 분류, 100 g 또는 1회 제공량 기준 영양 성분, 파일(CSV/XLSX)과 Open API | 정확한 데이터셋 명칭·파일 구조·갱신 주기, 공공누리 유형(출처 표시 조건), 1회 제공량 컬럼 유무 |
| 국가표준식품성분표 | 농촌진흥청 국립농업과학원 | 원재료(곡류·육류·채소 등) 위주, 영양 항목이 넓음 | 가공식품이 적어 이 앱의 주 대상(포장 식품)과 맞는지 |

둘 다 공공누리 제1유형(출처 표시)일 가능성이 높지만 **포털에서 직접 확인한 뒤** 이 표를 갱신한다. 출처 표시 문구는 설정 화면이나 영양 상세에 둔다.

## 3. 데이터 모델 (제안)

사용자 데이터와 분리된 **전역 읽기 전용 테이블**로 둔다. `user_id`가 없는 유일한 업무 테이블이므로 NFR-04 격리 규칙의 예외임을 [`erd.md`](erd.md)에 명시한다.

```
food_items
  id              uuid PK
  source          text        -- 'mfds' | 'rda' 등 데이터셋 식별자
  source_id       text        -- 원본 식별자 (source, source_id) 유니크
  dataset_version text        -- 가져온 파일 버전·날짜
  name            text
  category        text null
  maker           text null   -- 제조사·브랜드
  serving_size_g  numeric null -- 1회 제공량 (있을 때만)
  basis_amount_g  numeric     -- 영양 기준량, 보통 100
  kcal, carb_g, protein_g, fat_g  numeric null   -- 없는 값은 null (0 이 아님)
  sugar_g, sodium_mg, sat_fat_g   numeric null   -- 선택. 1차는 4대 영양소만 화면에 표시
  raw             jsonb       -- 원본 행 (추후 항목 추가 대비)
  imported_at     timestamptz
```

- 검색: 1차는 `ILIKE '%q%'` + `name` 일반 인덱스로 시작하고, 느리면 `pg_trgm` GIN 인덱스로 바꾼다(원시 SQL 마이그레이션 필요, DEC-055 의 CI 검사와 충돌하지 않는지 확인).
- 연결: `products.food_item_id uuid null` (SetNull). `NutritionSource` enum 에 `public_db` 추가. `ProductNutritionVersion` 은 값을 **복사**해 저장하므로 공공 DB 갱신이 과거 스냅샷·현재 영양을 바꾸지 않는다(NFR-02).
- 단위: 공공 DB 기준은 g 이므로 제품 영양 기준 단위는 `g`(D-11). `stock_unit=ea` 제품은 `pack_weight_g` 가 있어야 환산되고, 없으면 "1 단위 중량을 입력하세요" 안내.

## 4. 가져오기 절차 (제안)

1. 파일을 받아 `apps/api/scripts/import-food-db.mjs` 로 변환·upsert 한다. `(source, source_id)` 기준으로 갱신하고 사라진 행은 지우지 않는다(참조 보존).
2. `dataset_version` 에 파일명·날짜를 남기고 결과(행 수·건너뜀·오류)를 로그로 남긴다.
3. 운영은 VM 에서 수동 1회 실행, 갱신은 분기 1회 정도. 자동 동기화는 만들지 않는다.
4. 저장소에는 라이선스가 허용하는 범위에서 **샘플 50건 내외**만 테스트 픽스처로 둔다. 전체 파일은 커밋하지 않는다.
5. 크기: 수만~수십만 행, 행당 1 KB 미만을 가정하면 수십~수백 MB. 2 GB VM(DEC-010)에서 인덱스 포함 메모리를 실측한 뒤 `raw` 컬럼 유지 여부를 정한다.

## 5. API·화면 (제안)

| 항목 | 내용 |
| --- | --- |
| `GET /food-items?q=&limit=` | 로그인 필요. 이름 부분 일치, 최대 20건. 응답: 이름·제조사·분류·기준량·4대 영양소·출처 |
| `POST /products` / `POST /products/{id}/nutrition` | `foodItemId` 옵션. 서버가 값을 복사하고 `source=public_db`, 기준량 `basis_amount_g` g 로 저장. 사용자가 값을 고치면 `manual_estimate` |
| S-31 제품 등록 | "공공 DB에서 찾기" 버튼 → 검색 시트 → 선택 시 이름·제조사·영양 미리 채움 |
| S-33 영양 입력 | "DB 값 가져오기" 버튼. 기존 값이 있으면 새 버전으로 저장(D-03 과 동일한 미상 보완 흐름 적용 가능) |

## 6. 단계 배치와 결정 필요 사항

- 권고 배치: 단계 2(재고 화면·예측·알림) 뒤, 단계 3(OCR) 앞의 **단계 2.5**. OCR 보다 비용이 없고 데이터 정확도가 높아 먼저 두는 편이 효과가 크다.
- 결정 필요(§F):
  1. 데이터셋 선택과 라이선스·출처 표시 문구 확인.
  2. 저장 영양 항목 범위: 4대 영양소만인지, 당·나트륨까지인지.
  3. 외부 식사(S-12)에서도 검색을 열지, 제품 등록에만 둘지.
  4. 갱신 주기와 담당(수동).
- 검증 기준: 샘플 import → 검색 → 제품 생성 → 영양 값이 원본과 일치, 공공 DB 행을 바꿔도 기존 제품 영양·스냅샷이 변하지 않음, 타 사용자 격리 영향 없음(전역 읽기 전용).
